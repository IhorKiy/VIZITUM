# Data Model

Reference for the implemented database schema. Source of truth: `prisma/schema.prisma` (migrations in `prisma/migrations/`). This is the current state; `docs/vizitum-low-level-technical-design.md` §DB describes design intent and may differ. Update this document in the same change as any schema change.

**39 models**, one shared PostgreSQL database. Conceptual split: `platform_*` tables (tenant registry, platform identity, operations) vs tenant-owned business tables (every one carries `tenantId`). Prisma migrations are the only allowed way to change production schema.

## Conventions

- IDs: `cuid()` strings.
- Tenant-owned tables: `tenantId` + `createdAt` + `updatedAt`; soft delete via `deletedAt` where user-facing records can be removed (`users`, `chains`, `locations`, `location_contacts`, `products`, `tasks`, `visit_notes`, `storage_objects`). `announcements` withdraws via `archivedAt` instead — same idea, different name, because a withdrawn notice is a published thing that stopped applying rather than a record that should never have existed.
- Uniqueness is tenant-scoped where it matters: `users @@unique([tenantId, email])`, `route_template_items @@unique([tenantId, routeTemplateId, sequence])`, `tenant_settings @@unique([tenantId, key])`. `products` and `locations` uniqueness on `(tenantId, externalCode)` is a **partial** unique index scoped to live rows (`WHERE deletedAt IS NULL`, migrations `20260713120000_product_external_code_partial_unique` and `20260718090000_location_external_code_partial_unique`) — not a plain `@@unique`, so a soft-deleted row frees its externalCode for re-import/re-create (matches the `deletedAt: null` create + import pre-checks). `route_plans` uniqueness on `(tenantId, representativeUserId, planDate)` is likewise **two partial** unique indexes (migration `20260721062916_route_plan_multi_per_day`): `route_plans_rep_date_template_key` scoped to `WHERE routeTemplateId IS NOT NULL` (a representative can hold several template-based plans on the same day, one per distinct template, but not the same template twice) and `route_plans_rep_date_no_template_key` scoped to `WHERE routeTemplateId IS NULL` (still at most one template-less manual plan per day). Prisma can't express partial unique indexes, so they're managed via raw SQL and omitted from `schema.prisma`.
- Phone numbers (`platform_tenants.contactPhone`, `users.phone`, `location_contacts.phone`): canonical storage format is **E.164** (`+380671234567`). Every write path parses input via `src/common/phone.ts` against the tenant's `phoneCountry` (`+`-prefixed input is accepted as international regardless of country); display formatting derives from the stored E.164 value. Legacy values that predate normalization and don't parse are left as-is by the best-effort backfill (`npm run backfill:phone-e164`) and never block reads or non-phone updates — re-validation triggers only when the phone field itself changes.

## Platform group

| Model | Table | Purpose |
| --- | --- | --- |
| `PlatformTenant` | `platform_tenants` | Tenant registry: `slug` (unique, used in URLs), `status` (TenantStatus — doubles as the plan tier for a live tenant: `pilot`/`team`/`business`, or `suspended`/`archived`; there is no separate plan field), `productMode`, `segmentTemplate`, `databasePlacement` (shared/dedicated), `country`, `timezone`, `language`, `phoneCountry` (String?, nullable — ISO 3166-1 alpha-2 default country for phone entry, set by the platform owner; new tenants default it from `country` when that is a valid ISO code; `null` on legacy tenants means phone inputs only accept `+`-prefixed international numbers), `contactName`/`contactEmail`/`contactPhone` (String?, nullable — primary contact captured at creation and shown in the platform console's Tenant information block; the `POST /platform/tenants` create flow requires all three, older rows predating them are null), `adminLimit` (Int?, nullable — the max active `company_admin` users, enforced by `UsersService`. NULL means the cap derives from the plan tier: pilot 0, team 1, business 2, suspended 0, other/legacy statuses fall back to 2 = `DEFAULT_ADMIN_LIMIT`; see `adminCapForStatus`/`resolveAdminCap` in `src/modules/users/users.types.ts`. A number is a deliberate platform-owner override, set/cleared via `PATCH /platform/tenants/:tenantId`. Platform tenant API responses expose the effective cap as `adminLimit`, the raw override as `adminLimitOverride`, and the plan-derived value as `adminLimitPlanDefault`). Two-stage deletion markers: `archivedAt` (set by archive), `purgeRequestedAt` (platform owner's explicit early-purge mark on an archived tenant; cleared by unarchive), `purgeStartedAt` (stamped by the purge worker before it deletes anything — the point of no return: unarchive refuses once set). The `purge` worker deletes an eligible tenant's data and finally the row itself; `PlatformOperationEvent` rows survive via `onDelete: SetNull`. |
| `PlatformUser` | `platform_users` | Platform-owner identity, separate from tenant `users`: `email` (globally unique), `passwordHash`, `status` (PlatformUserStatus: active/suspended). Holds the `platform_owner` role. Second factor: `totpSecret` + `totpConfirmedAt` (both set only once a generated code has proved an authenticator holds the secret; the secret is stored encrypted with AES-256-GCM — see `TOTP_ENCRYPTION_KEY` in [environment.md](environment.md) — because verifying a code needs the secret itself, so unlike a password it cannot be hashed), `totpLastUsedStep` (Int?, the TOTP step of the last accepted code: one code is valid across three steps for clock drift, so a code whose step is not greater than this is refused and the same six digits cannot be spent twice) and `totpRecoveryCodeHashes` (SHA-256 of ten single-use codes, struck from the list as they are spent). Nullable so an owner can still sign in and enrol — the login flow issues no session until enrolment completes. |
| `PlatformMfaChallenge` | `platform_mfa_challenges` | The short-lived state between "the password was right" and "a session exists": `tokenHash` (unique), `purpose` (login/enrollment), `pendingSecret` (enrolment only — the candidate secret, held here rather than on the user until confirmed), `expiresAt`, `consumedAt`. In the database rather than a signed cookie so it can be consumed exactly once and revoked server-side. |
| `PlatformSession` | `platform_sessions` | Platform-owner session (token hash, expiry, revoke) for `vizitum_platform_session`; mirrors `sessions` but keyed by `platformUserId`, no `tenantId`. |
| `PlatformProvisioningJob` | `platform_provisioning_jobs` | Tenant provisioning job state (JobStatus, step, error). Legacy: tenants are created straight into `pilot` and no longer get a job row; existing rows are kept for history and still readable via `GET /platform/tenants/:tenantId`. |
| `PlatformOperationEvent` | `platform_operation_events` | Platform-level event log (`eventType`, `metadata`, optional tenant). Holds the tenant lifecycle events written by `PlatformService`/`TenantPurgeService` and the platform sign-in trail (`platform.login_succeeded`/`login_failed`/`logged_out`, from `AuthAuditService`), plus `platform.reauth_failed` — a code refused in front of a destructive action, which unlike the sign-in rows *does* carry the `tenantId` being acted on, because what was being attempted is the point of the record — the sign-in rows carry no `tenantId`, since a platform owner reaches every tenant. |

## Field data group

| Model | Table | Purpose |
| --- | --- | --- |
| `Chain` | `chains` | Retail chain/network a location belongs to (ChainStatus active/archived). Canonical per-tenant list, unique on `(tenant, name)` and `(tenant, externalCode)`; `Location.chainId` → `Chain` is optional and `SetNull` on chain delete. |
| `Location` | `locations` | Visit points: address fields, optional lat/long, LocationStatus (active/inactive only — deactivation), optional `chainId` → `Chain`, optional `categoryId` → `LocationCategory` (`Restrict` on delete — see below). Archival is the shared soft-delete (`deletedAt`), exposed as `archived` on responses and the `status=archived` list filter; `DELETE /locations/:id` archives, `POST /locations/:id/restore` reverses it. Legacy rows written with `status='archived'` before this model are backfilled to `deletedAt`+`inactive` by migration `20260718090500_location_legacy_archived_backfill`. The former free-text `type` column was dropped and backfilled into `LocationCategory` rows by migration `20260718100000_location_category_dictionary` (one category per tenant per distinct case-insensitive value, first-seen casing kept as the display name). The `region` and `territory` columns still exist (and are indexed) but are dormant — not exposed in the UI, API or CSV import on the Pilot/Team surface; they are reserved for the Business tier's regional/territory breakdown. `notes` is writable by any tenant admin via `PATCH /locations/:id`, and separately by an assigned `field_representative` via the narrower, ownership-scoped `PATCH /locations/:id/notes` (field-zone "location note" card) — see [permissions.md](permissions.md). |
| `LocationContact` | `location_contacts` | Contacts attached to a location (`phone` is stored as E.164 — see the phone note below). Writable by any tenant admin, and separately by an assigned `field_representative` (ownership-scoped, same `location_notes`/`contacts` `_manage_own` pattern as `LocationPotential`/`LocationAssortment` below) — see [permissions.md](permissions.md) and [api-reference.md](api-reference.md). |
| `LocationAssignment` | `location_assignments` | Representative ↔ location link with AssignmentStatus; unique per (tenant, location, representative). |
| `LocationCategory` | `location_categories` | Curated per-tenant category labels for grouping locations (managed from the admin Locations screen). Names are unique per tenant **case-insensitively** — enforced by a functional unique index on `(tenantId, lower(name))` (raw SQL, since Prisma can't express it declaratively), so "Bakery" and "bakery" can't coexist; the display name is stored exactly as typed. Unlike `ProductCategory`, `Location.categoryId` is a real FK (`onDelete: Restrict`): deleting a category still assigned to locations is rejected (409 `LOCATION_CATEGORY_IN_USE`) instead of silently orphaning or cascading. |
| `Product` | `products` | SKU catalog. `notApplicable` is a **deprecated** legacy flag — no longer read/written by the web UI (kept as a column, still accepted by the API); see api-reference Products note. Soft-deleted via `deletedAt` (all reads filter `deletedAt: null`). |
| `ProductCategory` | `product_categories` | Curated per-tenant category labels for grouping products (managed from the admin Products screen). Names are unique per tenant **case-insensitively** — enforced by a functional unique index on `(tenantId, lower(name))` (raw SQL, since Prisma can't express it declaratively), so "Beverages" and "beverages" can't coexist; the display name is stored exactly as typed. Hard-deleted — no FK from `products.category`, which stays a free-text string; renames cascade case-insensitively to matching `products.category` values. |
| `LocationPotential` | `location_potentials` | Per-location, per-`ProductCategory` sales potential estimate: `potentialDate` (`@db.Date`), `potentialAmount`, three-month plan (`planMonth1/2/3`), `comment`. Unique per (tenant, location, category) — `PUT /locations/:locationId/potential/:productCategoryId` is an idempotent upsert on that key, not create-then-patch. `productCategoryId` is `Restrict` on delete (like `Location.categoryId` → `LocationCategory`); `locationId` is `Cascade`. Hard rows, no soft delete — an attribute table like `LocationAssignment`, not a document. A location's soft-delete doesn't cascade (only a hard delete does), so these rows outlive an archived location; the location-insights summary explicitly filters `location: { deletedAt: null }` on every aggregate to exclude them. See [permissions.md](permissions.md) and [api-reference.md](api-reference.md). |
| `LocationAssortment` | `location_assortment` | Per-location, per-`Product` assortment tracking, with **two owners on one row**: the manager authors `shouldBeListed` (the matrix — what this outlet must carry, and the "required" set for coverage), while `status` (AssortmentStatus: in_stock/out_of_stock — distinct from, and never merged with, `Product.status`) and `lastCheckedAt` (`@db.Date`) record what was actually seen on the shelf. `status` is **nullable with no default**: `null` means "in the matrix, never yet confirmed on a shelf", so a matrix a manager has just typed in reads as 0% covered rather than fully covered before anyone has visited. Those two field-owned columns are written in exactly one place — confirming a visit report whose `confirmedData.fieldReport.shelfChecked` is `true`, inside that confirm's own transaction (`src/modules/visits/shelf-check.ts`, see [api-reference.md](api-reference.md)) — so coverage tracks shelves rather than how diligently someone filled in a form. That write is monotonic: it skips rows whose `lastCheckedAt` is already newer than the confirmation's own date, since reports are confirmed whenever the rep gets to them rather than in visit order, and `visitDate` arrives from the client unchecked. Every status predating that write-back was cleared once by `20260727150000_reset_unconfirmed_assortment_status` — nothing could have confirmed a shelf before it existed, and the old modal's status select defaulted to `in_stock`, so those values were a form default at least as often as a judgement. Unique per (tenant, location, product); both `locationId` and `productId` are `Cascade` on delete. Coverage (`round(inStock(required)/count(required)*100)`, `0` when there are no required rows) is computed purely from these rows — `Product.category` is free text and is never joined for this purpose. Hard rows, no soft delete — a soft-deleted (not hard-deleted) location or product doesn't cascade, so these rows outlive both; `GET .../assortment` and the location-insights summary both filter `location: { deletedAt: null }` and `product: { deletedAt: null }` to exclude them from coverage and problem-product lists. |
| `Announcement` | `announcements` | A manager-authored notice shown to every field representative for as long as its window is open: `title`, `body`, and an **inclusive, date-only** `startsAt`/`endsAt` pair (`@db.Date`), interpreted against the tenant's own calendar day so "until the 31st" covers the whole 31st for the person in the field. There is no recipient table — the audience is every representative, so targeting one would only be a list to keep in sync with the roster. Withdrawing early sets `archivedAt` (no hard delete, and no `deletedAt`): the read receipts below are the record that the team was told, and deleting the row would take that with it. `createdByUserId` is `SetNull`, so an announcement outlives the manager who wrote it. State (`scheduled`/`active`/`finished`/`archived`) is **derived** from the window and `archivedAt` on every read, never stored — nothing has to run for an announcement to start or expire — and it also decides editability: once a row resolves to `finished` or `archived` the service refuses a `PATCH`, since receipts against it attest to that text. |
| `AnnouncementReadReceipt` | `announcement_read_receipts` | One row the first time a representative marks an announcement read. `@@unique([tenantId, announcementId, userId])` is what makes `POST /announcements/:id/read` idempotent — a second tap keeps the original `readAt` rather than resetting it, so "read" means "first saw it". Hard rows with no soft delete, like `LocationAssignment`; both `announcementId` and `userId` are `Cascade`, so withdrawing is the only way to stop showing a notice without discarding who acknowledged it. Feeds the manager board's read tally and the field zone's unread badge. The `_count` is **filtered** to receipts from active `field_representative` users, matching what `recipientCount` counts — managers hold `announcements.read` too, and an unfiltered numerator could exceed its own denominator. Indexed on `announcementId` alone as well (migration `20260728180000_announcement_receipt_announcement_index`): the unique constraint leads with `tenantId`, so it can serve neither that per-row count nor the delete cascade. |

## Routes & visits group

| Model | Table | Purpose |
| --- | --- | --- |
| `RoutePlan` | `route_plans` | A representative can hold several plans on the same `planDate` — one per distinct `routeTemplateId`, plus at most one template-less manual plan (see the partial-index note above) — each independently a RouteStatus lifecycle (draft→published→in_progress→completed/cancelled). Optional `routeTemplateId` → `RouteTemplate` (`SetNull` on template delete) records which named template (if any) this date was assigned from — set by `POST /routes/templates/:templateId/assign` and `POST /routes/templates/copy-month`; a plan created directly via `POST /routes` has no template. |
| `RouteItem` | `route_items` | Ordered stop (`sequence` unique within plan) with RouteItemStatus (**planned / visited / skipped**), planned time window, `skipReason`. At most one visit per item (`Visit.routeItemId` unique). `skipReason` is free text with two writers: a rep's own words via `PATCH /routes/:routePlanId/items/:itemId`, and a raw `VisitCancellationReason` token stamped by visit cancellation. Nothing renders the column today — any future UI must translate a known token (`common.labels.cancelReason_*`) and fall back to showing free text verbatim. |
| `RouteTemplate` | `route_templates` | A representative's reusable, named stop list (`name`, no uniqueness constraint — reps may reuse names), independent of any date. Never drives visits/reports directly; assigning it to a date copies its items into a real `RoutePlan`/`RouteItem`s (see above). |
| `RouteTemplateItem` | `route_template_items` | Ordered stop (`sequence` unique within template) on a `RouteTemplate`: just `locationId` + `sequence`, no status/time-window/skip fields (those only make sense once a stop is materialized onto a dated `RoutePlan`). Hard-deleted (`DELETE /routes/templates/:templateId/items/:itemId`) — unlike `RouteItem`, a template stop has no visit history to preserve. |
| `Visit` | `visits` | Visit lifecycle (VisitStatus: draft/in_progress/completed/cancelled) with `startedAt`/`completedAt`/`cancelledAt`; links location, representative, optional route item. Cancelling (only via `POST /visits/:visitId/cancel`) additionally records a required `cancellationReason` (VisitCancellationReason: location_closed/client_unavailable/route_changed/other) and optional `cancellationComment` (≤500 chars); both are null on every non-cancelled visit and on visits cancelled before the columns existed. A cancelled visit keeps its `routeItemId` — the visit↔stop link survives for reporting even though the stop is flipped to `skipped`. Placing a visit in time means `COALESCE(startedAt, createdAt)` (a never-started visit has no `startedAt`), and that reaches Postgres in **two different shapes**, so it takes two families of index. The day summary sends the `COALESCE` literally — served by the expression indexes `visits_tenant_representative_period_idx` and `visits_tenant_period_idx` in migration `20260728120000_visit_period_indexes`, which live there rather than in this schema because Prisma cannot express an index on an expression (`prisma migrate diff` does not report them as drift). The list (`findMany`/`count`/`groupBy`) goes through the ORM, which expands the same intent into `startedAt >= x OR (startedAt IS NULL AND createdAt >= x)` — a bitmap OR no expression index can match; migration `20260728130000_visit_list_period_indexes` adds the four plain indexes that serve it (`[tenantId, representativeUserId, startedAt|createdAt]`, `[tenantId, startedAt|createdAt]`, declared as `@@index` on the model), one per branch per scope, with the `createdAt` pairs doubling as `ORDER BY createdAt DESC` support. Measured on 300k rows: the tenant-wide list was a sequential scan for all three queries before them. A third pair, `visits_tenant_representative_status_period_idx` and `visits_tenant_status_period_idx` (migration `20260728160000_visit_history_start_indexes`, hand-written for the same reason as the first pair), carries `status` between the scope columns and the same expression: they serve the day summary's `historyStart` boundary (`MIN(COALESCE(startedAt, createdAt))`, scoped but unbounded in time) when a status filter is on. Without them that MIN walked to its first match — 15k shared buffers for a representative with 15000 visits and none of the selected status, 299k tenant-wide for a status that only exists in recent rows. Composite rather than one partial index per status: reads measured equal (3-4 buffers either way), so two objects and no migration per future status won over partial's ~8% cheaper writes and ~10% smaller footprint. **None of the three pairs is redundant** — dropping the plain expression pair sends the tenant-wide day-summary `GROUP BY` back to a parallel sequential scan (405 → 3910 buffers) and the unfiltered boundary to a bitmap scan (4 → 223), because a query with no status filter gets no sorted range out of an index with `status` in the middle. | Carries an optional `clientVisitId` — the id a device minted when the rep started the visit with no signal — unique per tenant (`@@unique([tenantId, clientVisitId])`) and null for every visit started before it existed; Postgres admits unlimited nulls in a unique index, so no backfill. It is the idempotency key for a deferred create and doubles as a resolvable id: visit lookups accept either it or `id`, so a URL opened offline survives the sync. Resolved as two separate queries, `id` first and `clientVisitId` only as a fallback — never a single `OR` — because `clientVisitId` is client-supplied and a device (or a malicious rep) could otherwise mint one equal to another visit's real `id`; an `OR` would let the lookup return either matching row indeterminately, while the two-step order guarantees a real server id always wins over a client-minted collision. Written when the row is *created* and never after — a deferred start that adopts an existing visit instead of creating one records its id in `VisitClientAlias` (below), which the lookup tries third and last, for the same ordering reason. Deliberately not the primary key — the server keeps minting its own cuid. See [api-reference.md](api-reference.md) for the replay and route-slot conflict rules.
| `VisitClientAlias` | `visit_client_aliases` | Client-minted ids that resolve to a visit they did **not** create. `Visit.clientVisitId` covers the ordinary deferred start, where the id the phone minted becomes the id of the row the server creates; it cannot cover the *adopt* outcome, where a start arriving to find the rep's own visit already open on that stop is handed that visit instead. Two devices — or two retries whose responses were both lost — can reach the same open visit carrying two different minted ids, and a single column takes only the first: the second then has nothing to replay onto, re-derives the route slot from scratch on its next retry, and (if the adopted visit has closed by then) creates a second, unwanted, unlinked visit for a stop already done. So every adopt writes a row here. `@@unique([tenantId, clientVisitId])` is tenant-scoped like the column it complements, and is also what makes recording one idempotent — a concurrent retry inserting the same id is skipped (`createMany` + `skipDuplicates`) rather than failing an adopt that has, either way, already succeeded. Rows are only ever added, never rewritten: a client id maps to one visit for good. `onDelete: Cascade` from the visit, but deleted explicitly before `visits` in the tenant purge, which never relies on cascades. No backfill — visits adopted before this existed carry their first adopter's id in `Visit.clientVisitId`, which the lookup still tries first, so nothing that resolves today stops resolving. |
| `VisitNote` | `visit_notes` | Text or audio note. Audio is referenced via `temporaryAudioObjectId` → `StorageObject` and is temporary processing data. |
| `Report` | `reports` | **The durable outcome of a visit** (one per visit, `visitId` unique): `templateCode` (SegmentTemplate), `schemaVersion`, `confirmedData` (JSON), `confirmedBy`/`confirmedAt`, optional `aiMetadata`, and an optional `clientRequestId` — the device's idempotency token for the confirm, unique per tenant (`@@unique([tenantId, clientRequestId])`). It is null for every report confirmed before the field existed and for any caller that does not send one, which the uniqueness tolerates because Postgres admits unlimited nulls in a unique index; no backfill is needed. It exists so a rep confirming with no signal can retry safely: the server matches the token and returns the first attempt's row rather than re-stamping `confirmedAt` and replacing the report's tasks. See [api-reference.md](api-reference.md) for the replay and reuse rules. Default status `confirmed`. `confirmedData` is freeform per `schemaVersion` — `manual.v1` is a plain `{ summary, resultStatus }`; the AI-draft path and the field visit-report form (`schemaVersion: "field-report.v1"`) both additionally carry `{ agreements, objections, mentionedProducts, nextActions, tasksToCreate, locationUpdates, confidence, requiresUserConfirmation }` (`src/modules/ai/ai-extraction.schemas.ts`), with `field-report.v1` further nesting the MG-shaped SKU/visit fields (`visitDate`, `outcome`, `orderPlaced`, `noOrderReason`, `stockStatus`, `productUpdates`, `nextAction`/`nextActionDueDate`) under a `fieldReport` key that manager report views don't otherwise render. `visitDate` is write-time validated on confirm (strict `YYYY-MM-DD` inside a 3-day backdating window, see [api-reference.md](api-reference.md)); rows confirmed before that validation may hold out-of-window or malformed values, and readers must tolerate them. The visit result is recorded as the fact `orderPlaced` (`boolean`) plus `noOrderReason` (only ever set when `orderPlaced` is `false`); `outcome`/`resultStatus` stay in the payload but are derived from that pair by `apps/web/lib/visit-result.ts` (`deriveVisitOutcome`), so manager views and reports confirmed before this change keep reading the same positive/neutral/negative field. The next-visit agreement is a single `nextAction` line (plus optional `nextActionDueDate`) that the form also emits as the one `tasksToCreate` entry — it replaced the four typed task drafts (assortment/merchandising/recommendation/special) the form used to collect separately. The shelf check writes one `productUpdates` row per SKU the rep tapped as absent (always `status: "out_of_stock"`, no quantities) plus a `shelfChecked` boolean, and `stockStatus` is derived from the former (`"out_of_stock"` when anything is missing, otherwise `null` — an untouched shelf check claims nothing). `shelfChecked` is the rep's explicit "I looked", and it is what licenses confirmation to write this location's `LocationAssortment` shelf state (see that model above): the unmarked required products are recorded present, the marked ones absent. It is a separate flag rather than an inference from an empty `productUpdates` because "nothing was missing" and "nobody checked" would otherwise be the same report. Note the deliberate coarseness: one missing SKU marks the whole location `out_of_stock`, so manager views reading location-level `stockStatus` now see a stronger signal than before, when the rep picked the location status by hand; `presentedProducts`/`presentedProductIds` are no longer written and only appear on reports confirmed before that change. A `problem` key (`{ type, note, photoObjectId, photoContentType }`) is written only when the rep recorded one — by exception, so an ordinary visit carries no problem object; `photoObjectId` points at a `visit_attachment` `StorageObject` registered via `POST /visits/:visitId/problem-photos/register` and read back through a presigned download URL (`POST /storage/objects/:storageObjectId/download-url`). That object carries an `expiresAt` until the report claiming it is confirmed — see the endpoint notes in [api-reference.md](api-reference.md) for why registering is not keeping. |
| `Task` | `tasks` | Follow-up work: `status` (TaskStatus: in_progress/done — created directly `in_progress`, the only transition is to `done`), `isPriority` boolean flag (a plain regular-vs-priority toggle, not a graded scale), optional assignee, location, visit, report, `dueDate`. `completedAt` is stamped on the move to `done` and cleared on the way back; a backfill migration (`20260721150000_task_done_completed_at_backfill`) makes the invariant hold for old rows too, so **every** done task has one — the done list filters and orders on it without a fallback. Two indexes carry that list in its two scopes, `[tenantId, assignedToUserId, status, completedAt]` (a representative's own finished work) and `[tenantId, status, completedAt]` (tenant-wide), with `completedAt` trailing the equality columns so the completion window's range scan and the `completedAt desc` ordering come off one index. A caller with only own-scope task permissions (no `tasks.read_team`/`tasks.update_team`) may create a task only with `assignedToUserId` equal to themselves — see [permissions.md](permissions.md). |
| `TaskStatusHistory` | `task_status_history` | Append-only per-task trail: `changedByUserId`, `oldStatus` (null on the creation row), `newStatus`, `createdAt`. One row written on task creation and one on every status change (`TasksService.createTask`/`updateTask`, same transaction as the write it records) — a dedicated table rather than `AuditEvent`, which is for admin/platform events. Returned as `Task.history` on `GET`/`POST`/`PATCH /tasks`; tasks that predate this table just have an empty `history` array, so the UI falls back to `Task.createdByUserId`/`createdAt` for the "created by" line. Hard rows, no soft delete — `taskId` is `Cascade` on delete. |

### Retention rule (product requirement)

Audio, transcript, and AI draft are **temporary processing data only**. After the report is confirmed, only the confirmed report plus minimal processing metadata (`Report.aiMetadata`) is retained. Temporary objects carry `expiresAt` and are removed by the cleanup worker (`src/worker.ts`). The sweep collects every temporary purpose (`temporary_audio`, `temporary_transcript`, `visit_attachment`) whose `expiresAt` has passed and whose bytes have not already been removed (`deletedAt: null`), regardless of `status` — a row can be `active` (an abandoned registration, or the field-report flow, which marks nothing) or `expired` (a writer done processing it) and either is collectable once past its expiry. Only the sweep itself may set `deletedAt`, and only after the R2 delete succeeds; a writer that stamps it without deleting anything would make the row permanently unsweepable — which is exactly what the two `temporary_audio`/`temporary_transcript` writers in `ai.service.ts` did before #148 (they stamped `deletedAt` in the same update that marked a row `expired`, no R2 delete involved). Migration `20260730130000_storage_temporary_deletedat_backfill` clears those false tombstones (`deletedAt` back to `NULL`, `status` to `expired`) so the sweep can collect the R2 bytes they were always supposed to remove; it never touches a row already `status: 'deleted'`, which is the sweep's own mark that R2 already confirmed those bytes gone.
