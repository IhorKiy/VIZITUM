# Data Model

Reference for the implemented database schema. Source of truth: `prisma/schema.prisma` (migrations in `prisma/migrations/`). This is the current state; `docs/vizitum-low-level-technical-design.md` §DB describes design intent and may differ. Update this document in the same change as any schema change.

**33 models**, one shared PostgreSQL database. Conceptual split: `platform_*` tables (tenant registry, platform identity, operations) vs tenant-owned business tables (every one carries `tenantId`). Prisma migrations are the only allowed way to change production schema.

## Conventions

- IDs: `cuid()` strings.
- Tenant-owned tables: `tenantId` + `createdAt` + `updatedAt`; soft delete via `deletedAt` where user-facing records can be removed (`users`, `chains`, `locations`, `location_contacts`, `products`, `tasks`, `visit_notes`, `storage_objects`).
- Uniqueness is tenant-scoped where it matters: `users @@unique([tenantId, email])`, `route_template_items @@unique([tenantId, routeTemplateId, sequence])`, `tenant_settings @@unique([tenantId, key])`. `products` and `locations` uniqueness on `(tenantId, externalCode)` is a **partial** unique index scoped to live rows (`WHERE deletedAt IS NULL`, migrations `20260713120000_product_external_code_partial_unique` and `20260718090000_location_external_code_partial_unique`) — not a plain `@@unique`, so a soft-deleted row frees its externalCode for re-import/re-create (matches the `deletedAt: null` create + import pre-checks). `route_plans` uniqueness on `(tenantId, representativeUserId, planDate)` is likewise **two partial** unique indexes (migration `20260721062916_route_plan_multi_per_day`): `route_plans_rep_date_template_key` scoped to `WHERE routeTemplateId IS NOT NULL` (a representative can hold several template-based plans on the same day, one per distinct template, but not the same template twice) and `route_plans_rep_date_no_template_key` scoped to `WHERE routeTemplateId IS NULL` (still at most one template-less manual plan per day). Prisma can't express partial unique indexes, so they're managed via raw SQL and omitted from `schema.prisma`.
- Phone numbers (`platform_tenants.contactPhone`, `users.phone`, `location_contacts.phone`): canonical storage format is **E.164** (`+380671234567`). Every write path parses input via `src/common/phone.ts` against the tenant's `phoneCountry` (`+`-prefixed input is accepted as international regardless of country); display formatting derives from the stored E.164 value. Legacy values that predate normalization and don't parse are left as-is by the best-effort backfill (`npm run backfill:phone-e164`) and never block reads or non-phone updates — re-validation triggers only when the phone field itself changes.

## Platform group

| Model | Table | Purpose |
| --- | --- | --- |
| `PlatformTenant` | `platform_tenants` | Tenant registry: `slug` (unique, used in URLs), `status` (TenantStatus — doubles as the plan tier for a live tenant: `pilot`/`team`/`business`, or `suspended`/`archived`; there is no separate plan field), `productMode`, `segmentTemplate`, `databasePlacement` (shared/dedicated), `country`, `timezone`, `language`, `phoneCountry` (String?, nullable — ISO 3166-1 alpha-2 default country for phone entry, set by the platform owner; new tenants default it from `country` when that is a valid ISO code; `null` on legacy tenants means phone inputs only accept `+`-prefixed international numbers), `contactName`/`contactEmail`/`contactPhone` (String?, nullable — primary contact captured at creation and shown in the platform console's Tenant information block; the `POST /platform/tenants` create flow requires all three, older rows predating them are null), `adminLimit` (Int?, nullable — the max active `company_admin` users, enforced by `UsersService`. NULL means the cap derives from the plan tier: pilot 0, team 1, business 2, suspended 0, other/legacy statuses fall back to 2 = `DEFAULT_ADMIN_LIMIT`; see `adminCapForStatus`/`resolveAdminCap` in `src/modules/users/users.types.ts`. A number is a deliberate platform-owner override, set/cleared via `PATCH /platform/tenants/:tenantId`. Platform tenant API responses expose the effective cap as `adminLimit`, the raw override as `adminLimitOverride`, and the plan-derived value as `adminLimitPlanDefault`). Two-stage deletion markers: `archivedAt` (set by archive), `purgeRequestedAt` (platform owner's explicit early-purge mark on an archived tenant; cleared by unarchive), `purgeStartedAt` (stamped by the purge worker before it deletes anything — the point of no return: unarchive refuses once set). The `purge` worker deletes an eligible tenant's data and finally the row itself; `PlatformOperationEvent` rows survive via `onDelete: SetNull`. |
| `PlatformUser` | `platform_users` | Platform-owner identity, separate from tenant `users`: `email` (globally unique), `passwordHash`, `status` (PlatformUserStatus: active/suspended). Holds the `platform_owner` role. |
| `PlatformSession` | `platform_sessions` | Platform-owner session (token hash, expiry, revoke) for `vizitum_platform_session`; mirrors `sessions` but keyed by `platformUserId`, no `tenantId`. |
| `PlatformProvisioningJob` | `platform_provisioning_jobs` | Tenant provisioning job state (JobStatus, step, error). Legacy: tenants are created straight into `pilot` and no longer get a job row; existing rows are kept for history and still readable via `GET /platform/tenants/:tenantId`. |
| `PlatformOperationEvent` | `platform_operation_events` | Platform-level event log (`eventType`, `metadata`, optional tenant). |

## Field data group

| Model | Table | Purpose |
| --- | --- | --- |
| `Chain` | `chains` | Retail chain/network a location belongs to (ChainStatus active/archived). Canonical per-tenant list, unique on `(tenant, name)` and `(tenant, externalCode)`; `Location.chainId` → `Chain` is optional and `SetNull` on chain delete. |
| `Location` | `locations` | Visit points: address fields, optional lat/long, LocationStatus (active/inactive only — deactivation), optional `chainId` → `Chain`, optional `categoryId` → `LocationCategory` (`Restrict` on delete — see below). Archival is the shared soft-delete (`deletedAt`), exposed as `archived` on responses and the `status=archived` list filter; `DELETE /locations/:id` archives, `POST /locations/:id/restore` reverses it. Legacy rows written with `status='archived'` before this model are backfilled to `deletedAt`+`inactive` by migration `20260718090500_location_legacy_archived_backfill`. The former free-text `type` column was dropped and backfilled into `LocationCategory` rows by migration `20260718100000_location_category_dictionary` (one category per tenant per distinct case-insensitive value, first-seen casing kept as the display name). The `region` and `territory` columns still exist (and are indexed) but are dormant — not exposed in the UI, API or CSV import on the Pilot/Team surface; they are reserved for the Business tier's regional/territory breakdown. `notes` is writable by any tenant admin via `PATCH /locations/:id`, and separately by an assigned `field_representative` via the narrower, ownership-scoped `PATCH /locations/:id/notes` (field-zone "location note" card) — see [permissions.md](permissions.md). |
| `LocationContact` | `location_contacts` | Contacts attached to a location (`phone` is stored as E.164 — see the phone note below). Writable by any tenant admin, and separately by an assigned `field_representative` (ownership-scoped, same `location_notes`/`contacts` `_manage_own` pattern as `LocationPotential`/`LocationAssortment` below) — see [permissions.md](permissions.md) and [api-reference.md](api-reference.md). |
| `LocationAssignment` | `location_assignments` | Representative ↔ location link with AssignmentStatus; unique per (tenant, location, representative). |
| `LocationCategory` | `location_categories` | Curated per-tenant category labels for grouping locations (managed from the admin Locations screen). Names are unique per tenant **case-insensitively** — enforced by a functional unique index on `(tenantId, lower(name))` (raw SQL, since Prisma can't express it declaratively), so "Bakery" and "bakery" can't coexist; the display name is stored exactly as typed. Unlike `ProductCategory`, `Location.categoryId` is a real FK (`onDelete: Restrict`): deleting a category still assigned to locations is rejected (409 `LOCATION_CATEGORY_IN_USE`) instead of silently orphaning or cascading. |
| `Product` | `products` | SKU catalog. `notApplicable` is a **deprecated** legacy flag — no longer read/written by the web UI (kept as a column, still accepted by the API); see api-reference Products note. Soft-deleted via `deletedAt` (all reads filter `deletedAt: null`). |
| `ProductCategory` | `product_categories` | Curated per-tenant category labels for grouping products (managed from the admin Products screen). Names are unique per tenant **case-insensitively** — enforced by a functional unique index on `(tenantId, lower(name))` (raw SQL, since Prisma can't express it declaratively), so "Beverages" and "beverages" can't coexist; the display name is stored exactly as typed. Hard-deleted — no FK from `products.category`, which stays a free-text string; renames cascade case-insensitively to matching `products.category` values. |
| `LocationPotential` | `location_potentials` | Per-location, per-`ProductCategory` sales potential estimate: `potentialDate` (`@db.Date`), `potentialAmount`, three-month plan (`planMonth1/2/3`), `comment`. Unique per (tenant, location, category) — `PUT /locations/:locationId/potential/:productCategoryId` is an idempotent upsert on that key, not create-then-patch. `productCategoryId` is `Restrict` on delete (like `Location.categoryId` → `LocationCategory`); `locationId` is `Cascade`. Hard rows, no soft delete — an attribute table like `LocationAssignment`, not a document. A location's soft-delete doesn't cascade (only a hard delete does), so these rows outlive an archived location; the location-insights summary explicitly filters `location: { deletedAt: null }` on every aggregate to exclude them. See [permissions.md](permissions.md) and [api-reference.md](api-reference.md). |
| `LocationAssortment` | `location_assortment` | Per-location, per-`Product` assortment tracking: `shouldBeListed` (defines the "required" set for coverage), `status` (AssortmentStatus: in_stock/out_of_stock/to_order/not_relevant — distinct from, and never merged with, `Product.status`), `lastStock`/`lastOrder`/`lastSale`, `lastCheckedAt` (`@db.Date`), `comment`. Unique per (tenant, location, product); both `locationId` and `productId` are `Cascade` on delete. Coverage (`round(inStock(required)/count(required)*100)`, `0` when there are no required rows) is computed purely from these rows — `Product.category` is free text and is never joined for this purpose. Hard rows, no soft delete — a soft-deleted (not hard-deleted) location or product doesn't cascade, so these rows outlive both; `GET .../assortment` and the location-insights summary both filter `location: { deletedAt: null }` and `product: { deletedAt: null }` to exclude them from coverage and problem-product lists. |

## Routes & visits group

| Model | Table | Purpose |
| --- | --- | --- |
| `RoutePlan` | `route_plans` | A representative can hold several plans on the same `planDate` — one per distinct `routeTemplateId`, plus at most one template-less manual plan (see the partial-index note above) — each independently a RouteStatus lifecycle (draft→published→in_progress→completed/cancelled). Optional `routeTemplateId` → `RouteTemplate` (`SetNull` on template delete) records which named template (if any) this date was assigned from — set by `POST /routes/templates/:templateId/assign` and `POST /routes/templates/copy-month`; a plan created directly via `POST /routes` has no template. |
| `RouteItem` | `route_items` | Ordered stop (`sequence` unique within plan) with RouteItemStatus (**planned / visited / skipped**), planned time window, `skipReason`. At most one visit per item (`Visit.routeItemId` unique). `skipReason` is free text with two writers: a rep's own words via `PATCH /routes/:routePlanId/items/:itemId`, and a raw `VisitCancellationReason` token stamped by visit cancellation. Nothing renders the column today — any future UI must translate a known token (`common.labels.cancelReason_*`) and fall back to showing free text verbatim. |
| `RouteTemplate` | `route_templates` | A representative's reusable, named stop list (`name`, no uniqueness constraint — reps may reuse names), independent of any date. Never drives visits/reports directly; assigning it to a date copies its items into a real `RoutePlan`/`RouteItem`s (see above). |
| `RouteTemplateItem` | `route_template_items` | Ordered stop (`sequence` unique within template) on a `RouteTemplate`: just `locationId` + `sequence`, no status/time-window/skip fields (those only make sense once a stop is materialized onto a dated `RoutePlan`). Hard-deleted (`DELETE /routes/templates/:templateId/items/:itemId`) — unlike `RouteItem`, a template stop has no visit history to preserve. |
| `Visit` | `visits` | Visit lifecycle (VisitStatus: draft/in_progress/completed/cancelled) with `startedAt`/`completedAt`/`cancelledAt`; links location, representative, optional route item. Cancelling (only via `POST /visits/:visitId/cancel`) additionally records a required `cancellationReason` (VisitCancellationReason: location_closed/client_unavailable/route_changed/other) and optional `cancellationComment` (≤500 chars); both are null on every non-cancelled visit and on visits cancelled before the columns existed. A cancelled visit keeps its `routeItemId` — the visit↔stop link survives for reporting even though the stop is flipped to `skipped`. |
| `VisitNote` | `visit_notes` | Text or audio note. Audio is referenced via `temporaryAudioObjectId` → `StorageObject` and is temporary processing data. |
| `Report` | `reports` | **The durable outcome of a visit** (one per visit, `visitId` unique): `templateCode` (SegmentTemplate), `schemaVersion`, `confirmedData` (JSON), `confirmedBy`/`confirmedAt`, optional `aiMetadata`. Default status `confirmed`. `confirmedData` is freeform per `schemaVersion` — `manual.v1` is a plain `{ summary, resultStatus }`; the AI-draft path and the field visit-report form (`schemaVersion: "field-report.v1"`) both additionally carry `{ agreements, objections, mentionedProducts, nextActions, tasksToCreate, locationUpdates, confidence, requiresUserConfirmation }` (`src/modules/ai/ai-extraction.schemas.ts`), with `field-report.v1` further nesting the MG-shaped SKU/visit fields (`visitDate`, `outcome`, `orderPlaced`, `noOrderReason`, `stockStatus`, `productUpdates`, `nextAction`/`nextActionDueDate`) under a `fieldReport` key that manager report views don't otherwise render. The visit result is recorded as the fact `orderPlaced` (`boolean`) plus `noOrderReason` (only ever set when `orderPlaced` is `false`); `outcome`/`resultStatus` stay in the payload but are derived from that pair by `apps/web/lib/visit-result.ts` (`deriveVisitOutcome`), so manager views and reports confirmed before this change keep reading the same positive/neutral/negative field. The next-visit agreement is a single `nextAction` line (plus optional `nextActionDueDate`) that the form also emits as the one `tasksToCreate` entry — it replaced the four typed task drafts (assortment/merchandising/recommendation/special) the form used to collect separately. The shelf check writes one `productUpdates` row per SKU the rep tapped as absent (always `status: "out_of_stock"`, no quantities) and `stockStatus` is derived from it (`"out_of_stock"` when anything is missing, otherwise `null` — an untouched shelf check claims nothing). Note the deliberate coarseness: one missing SKU marks the whole location `out_of_stock`, so manager views reading location-level `stockStatus` now see a stronger signal than before, when the rep picked the location status by hand; `presentedProducts`/`presentedProductIds` are no longer written and only appear on reports confirmed before that change. A `problem` key (`{ type, note, photoObjectId, photoContentType }`) is written only when the rep recorded one — by exception, so an ordinary visit carries no problem object; `photoObjectId` points at a `visit_attachment` `StorageObject` registered via `POST /visits/:visitId/problem-photos/register` and read back through a presigned download URL (`POST /storage/objects/:storageObjectId/download-url`). That object carries an `expiresAt` until the report claiming it is confirmed — see the endpoint notes in [api-reference.md](api-reference.md) for why registering is not keeping. |
| `Task` | `tasks` | Follow-up work: `status` (TaskStatus: in_progress/done — created directly `in_progress`, the only transition is to `done`), `isPriority` boolean flag (a plain regular-vs-priority toggle, not a graded scale), optional assignee, location, visit, report, `dueDate`. A caller with only own-scope task permissions (no `tasks.read_team`/`tasks.update_team`) may create a task only with `assignedToUserId` equal to themselves — see [permissions.md](permissions.md). |
| `TaskStatusHistory` | `task_status_history` | Append-only per-task trail: `changedByUserId`, `oldStatus` (null on the creation row), `newStatus`, `createdAt`. One row written on task creation and one on every status change (`TasksService.createTask`/`updateTask`, same transaction as the write it records) — a dedicated table rather than `AuditEvent`, which is for admin/platform events. Returned as `Task.history` on `GET`/`POST`/`PATCH /tasks`; tasks that predate this table just have an empty `history` array, so the UI falls back to `Task.createdByUserId`/`createdAt` for the "created by" line. Hard rows, no soft delete — `taskId` is `Cascade` on delete. |

### Retention rule (product requirement)

Audio, transcript, and AI draft are **temporary processing data only**. After the report is confirmed, only the confirmed report plus minimal processing metadata (`Report.aiMetadata`) is retained. Temporary objects carry `expiresAt` and are removed by the cleanup worker (`src/worker.ts`).

## Enums

Defined in `prisma/schema.prisma` and mirrored in TypeScript where needed:

`TenantStatus` (draft/provisioning/ready/active retired — see `PlatformTenant` above; `pilot`/`team`/`business` double as the plan tier, plus `suspended`/`archived`), `ProductMode` (team/business), `DatabasePlacement` (shared/dedicated), `SegmentTemplate` (distribution/service/partner_account), `JobStatus`, `PlatformUserStatus` (active/suspended), `UserStatus`, `InviteStatus`, `InviteEmailStatus` (skipped/sent/failed — invite-email delivery outcome, see `Invite` above), `RoleCode`, `NavZone` (field/manager/admin/operations — frontend nav grouping, see `User.lastSelectedZone` above), `LocationStatus`, `ChainStatus` (active/archived), `AssignmentStatus`, `ProductStatus`, `AssortmentStatus` (in_stock/out_of_stock/to_order/not_relevant — `LocationAssortment` row status, see above), `RouteStatus`, `RouteItemStatus`, `VisitStatus`, `VisitNoteInputType` (text/audio), `ReportStatus` (draft/confirmed/discarded), `TaskStatus` (in_progress/done), `ImportType`, `ImportStatus`, `ImportIssueSeverity`, `AiJobType`, `AiJobStatus`, `StorageObjectStatus`, `StorageObjectPurpose` (temporary_audio/temporary_transcript/import_file/export_file/attachment/branding_logo/visit_attachment — `visit_attachment` is evidence tied to one visit's report, kept separate from the generic `attachment` so storage permissions and cleanup can treat it as a visit artifact).
