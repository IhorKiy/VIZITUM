# Executable Specification

This document maps behavior tests in `tests/` to product and platform rules that are already implemented. Treat these tests as executable specification: when a future change touches the same behavior, read the matching test before editing code and update the test in the same change if the intended behavior changes.

Design documents explain intent. This file records behavior that has been pinned by tests.

## How to use this map

- Start with this file when a task affects tenant isolation, imports, AI reporting, manual fallback, permissions, manager filters, storage, operations, logging or readiness.
- Use the listed tests to understand exact edge cases before relying on higher-level roadmap wording.
- Do not weaken or remove a tested rule unless the product decision is documented in the relevant spec or reference document.
- When adding Track B-E behavior, add or update a focused test and add it to this map.

## Product behavior contracts

| Test                                            | Contract                                                                                                                                            |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tests/auth-tenant-isolation.test.ts`           | Tenant-owned access is scoped by request context, not client-provided tenant identifiers. Cross-tenant data must not leak, invite acceptance with a page tenant slug must match the invite tenant, the platform bearer token stays operations-read only, and `PermissionGuard` bumps `lastSeenAt` on every authenticated platform-session request. |
| `tests/auth-zone-switch.test.ts`                | `POST /auth/zone` requires an active session (401 `AUTHENTICATION_REQUIRED`), rejects a zone not in `field`/`manager`/`admin`/`operations` (400 `INVALID_ZONE`) and a zone the caller's permissions don't cover per `src/modules/auth/zones.ts` (400 `ZONE_NOT_AVAILABLE`), persists and returns `lastSelectedZone` on success, and scopes the user lookup to `{ id: session.userId, tenantId: session.tenantId }` — same tenant-isolation shape as `switchRole`. |
| `tests/nav-zones.test.ts`                       | `apps/web/lib/navigation.ts`'s pure zone helpers: each nav item's zone tag, `availableZones` (including the `productsEnabled` filter and the `operations` zone via `platform.operations.read`), `resolveDefaultZone`'s stored-and-available/exactly-one/none order, `resolveZoneLanding`'s three outcomes, and the `team_manager` cross-zone overlap documented in [module-map.md](module-map.md) (pinned as intentional). |
| `tests/zone-permission-mirror.test.ts`          | The backend zone map (`ZONE_PERMISSIONS` in `src/modules/auth/zones.ts`, validates `POST /auth/zone`) stays an exact mirror of the frontend nav item definitions: same zone set, and per zone the same permission union as the `requiredPermissions` of that zone's items in `apps/web/lib/navigation.ts`. Fails on any drift — the failure mode it closes is the frontend offering a zone the backend then rejects with `ZONE_NOT_AVAILABLE` (or vice versa). |
| `tests/routes-permissions.test.ts`              | Route reads and route mutations honor role permissions and representative scope. Team-wide route management is broader than own-route management.   |
| `tests/users-service.test.ts`                   | Tenant-scoped user lifecycle behavior: invites, role assignment and status changes; a user can never be left with zero roles; admin-management actions (status/role changes on a `company_admin` target) run under the `admins.manage`/`admins.invite` gate and the anti-lockout check runs inside a serializable transaction to close a concurrent-request race. Directional protection (`ADMIN_MANAGEMENT_FORBIDDEN`/`SUPERADMIN_PROTECTED`) covers profile-field edits (name/phone) on a protected target too, not just status changes — `updateUser` checks unconditionally rather than only when status is changing. See `tests/tenant-superadmin-*.test.ts` for the superadmin-era admin-lockout/limit/protection rules that superseded the old unconditional "last company_admin" rule. |
| `tests/tenant-superadmin-admin-limit.test.ts`   | The tenant's Company Admin cap is enforced on invite, role-assign and reactivate (409 `TENANT_ADMIN_LIMIT`), and re-checked on invite acceptance to close the "multiple pending invites" gap. Exercises the explicit `PlatformTenant.adminLimit` override path (a set number wins). |
| `tests/tenant-admin-limit-plan.test.ts`         | When `PlatformTenant.adminLimit` is NULL, the Company Admin cap derives from the plan tier (`adminCapForStatus`: pilot 0, team 1, business 2, suspended 0; legacy/transient statuses fall back to `DEFAULT_ADMIN_LIMIT` = 2). `resolveAdminCap` prefers an explicit owner override over the plan cap. Enforcement blocks a company_admin on a pilot tenant, allows exactly one on team, and lets an override lift a pilot above its plan cap. |
| `tests/tenant-superadmin-directional-protection.test.ts` | Admin management (invite/suspend/reactivate/delete/re-role of a `company_admin`) requires `admins.invite`/`admins.manage`, held only by `tenant_superadmin` — a plain `company_admin` cannot act on another `company_admin` (403 `ADMIN_MANAGEMENT_FORBIDDEN`). No actor, including the superadmin itself, can change a `tenant_superadmin` target's status or roles through `/admin/users/*` (409 `SUPERADMIN_PROTECTED`). |
| `tests/tenant-superadmin-lockout.test.ts`       | The tenant's sole active `tenant_superadmin` cannot be suspended, re-roled or deleted by anyone (409 `SUPERADMIN_PROTECTED`, including the superadmin acting on themselves) — this alone keeps at least one active superadmin per tenant, since the only flows that change who holds the role always activate the replacement before deactivating the previous one. Once a superadmin is active, the Company Admin count may drop to zero. |
| `tests/tenant-superadmin-bootstrap-fallback.test.ts` | Tenants with no active superadmin yet (not migrated) fall back to the pre-existing "keep at least one active company_admin" rule (409 `TENANT_LAST_ADMIN`), so existing tenants aren't bricked before the platform owner invites/promotes their first superadmin. |
| `tests/tenant-superadmin-replacement.test.ts`   | Accepting a new superadmin invite demotes the previously active superadmin to a suspended `company_admin` in the same transaction (a role swap, not just deactivation — otherwise `SUPERADMIN_PROTECTED` would make that account permanently unreachable); exactly one active superadmin afterward. `PlatformService.promoteToSuperadmin` swaps an active Company Admin's role in place and demotes any prior active superadmin the same way. |
| `tests/manager-list-filters.test.ts`            | Manager visit/task lists support operational filters without escaping tenant scope or changing list semantics.                                      |
| `tests/settings-service.test.ts`                | Tenant settings (company name, IANA time zone, products-applicable) validate input and persist correctly; only `company_admin` can read/manage them. |
| `tests/import-templates.test.ts`                | Downloadable onboarding templates exist for `users`, `locations`, `contacts`, `products` and `initial_visit_task_plan`; unsupported downloads fail. |
| `tests/import-csv-parser.test.ts`               | CSV import parsing handles supported CSV syntax and parser errors consistently.                                                                     |
| `tests/import-xlsx-parser.test.ts`              | XLSX import parsing maps workbook rows into the same validation path as CSV imports.                                                                |
| `tests/import-sample-pack.test.ts`              | The first-pilot synthetic sample import pack uses approved headers and parseable rows for every import template.                                    |
| `tests/import-validation-preview.test.ts`       | Imports use validate-preview-before-confirm semantics with row issues, counts and confirm eligibility.                                              |
| `tests/ai-extraction-schemas.test.ts`           | MVP AI extraction schemas exist for `distribution`, `service` and `partner_account`; outputs are strict and require user confirmation.              |
| `tests/ai-transcription-job.test.ts`            | Transcription jobs are tenant-scoped and produce controlled job states for audio note processing; a transcription input object must be registered on the same tenant visit by the current user. |
| `tests/ai-extraction-job.test.ts`               | Extraction jobs use tenant/report template context and store draft output without creating final business objects by themselves; `draftQuality` is persisted on the job row and survives re-reads of an already-succeeded job. |
| `tests/ai-draft-confirmation.test.ts`           | AI draft confirmation is the point where confirmed report data and follow-up task creation become business state; the returned `report` includes `createdTasks`/`createdTaskCount`, matching the same shape `GET /visits/:visitId/report` returns. |
| `tests/manual-report-after-ai-failure.test.ts`  | Manual report confirmation must work even when AI failed and must not depend on reading failed AI job state.                                        |
| `tests/ai-failed-job-cleanup.test.ts`           | Failed AI job and temporary processing cleanup follows the retention behavior implemented by the worker cleanup path.                               |
| `tests/ai-draft-quality.test.ts`                | Weak-output criteria from `docs/specs/ai-quality-spec.md` are encoded: missing required fields, empty summary, invalid result status or confidence below 0.6 mark a draft `needs_review` instead of blocking the visit. |
| `tests/ai-extraction-evaluation.test.ts`        | Extraction evaluation harness: anonymized fixtures exist per MVP template, answer keys use approved fields/statuses, scoring is order/case-insensitive and the 80% pilot accuracy threshold is enforced. |
| `tests/visit-audio-upload-registration.test.ts` | Audio upload registration creates the note/storage metadata needed for browser recording or upload fallback.                                        |

| `tests/operations-summary.test.ts`              | Operations summary exposes platform health counters through the allowed session or platform-token path.                                             |
| `tests/platform-auth.test.ts`                   | Platform-owner login authenticates a `PlatformUser` (normalized email), rejects unknown/suspended users and wrong passwords without creating a session, issues the `vizitum_platform_session` + `vizitum_platform_csrf` cookies with the full `platform_owner` permission set, and requires an active session for `me`. |
| `tests/csrf-platform-session.test.ts`           | Platform and tenant sessions each validate CSRF against only their own session/cookie pair (`vizitum_platform_csrf` / `vizitum_csrf`), with no cross-domain fallback — a tenant login's CSRF cookie can't satisfy a platform mutation, a request on one domain's routes backed only by the other domain's session skips CSRF and falls through to `PermissionGuard` instead of validating cross-domain, and a token signed with the wrong session's key is rejected regardless of which cookie it's placed in. |
| `tests/platform-tenant-creation.test.ts`        | Platform tenant creation validates name/slug/segment template, rejects duplicate slugs and non-IANA timezones, and canonicalizes casing/aliases on the selected timezone (e.g. `europe/kyiv`) via the shared `normalizeTimezone` helper — an omitted timezone falls back to a default resolved through the same canonicalization, so both paths converge on one stored form; creates a new tenant directly on the `pilot` plan/status with no provisioning job; list/get expose the registry. Tenant routes require a `platform_owner` session. |
| `tests/platform-tenant-management.test.ts`      | Tenant update validates each editable field (including `adminLimit`, and `timezone` must be a real IANA zone and is canonicalized rather than stored as the caller's literal string); `status` doubles as the plan tier (no separate plan field), assignable to `pilot`/`team`/`business`/`suspended` only — refuses `archived` (that's the archive action's job) and the retired `draft`/`provisioning`/`ready`/`active`, rejects empty payloads and edits to an already-archived tenant, and records `tenant.updated`; archive stamps `archivedAt`, records `tenant.archived`, and is idempotent; unarchive restores an archived tenant to `suspended` (not its pre-archive status), clears `archivedAt`, records `tenant.unarchived`, and is idempotent on a tenant that isn't archived. Platform owners invite/replace the tenant superadmin through tenant-scoped platform context (revoking any existing pending superadmin invite first), with platform + audit events; archived tenants are rejected. Platform owners can also promote an existing active Company Admin to superadmin in place, demoting any prior active superadmin. `getTenantSuperadmin` does not report a superadmin invite as pending once its `expiresAt` has passed, even though the DB row is still physically `status: "pending"` until revoked or replaced. |
| `tests/platform-tenant-purge-marking.test.ts`   | `POST /platform/tenants/:tenantId/purge` marks an **archived** tenant for purge without deleting anything: requires a `confirmSlug` echoing the tenant slug (mismatch/missing → 400 `TENANT_PURGE_CONFIRMATION_MISMATCH`, nothing changes), refuses non-archived tenants (409 `TENANT_NOT_ARCHIVED`), is idempotent when already marked or already purging, race-safe (conditional update, no duplicate `tenant.purge_requested` event). Unarchive stays the rescue hatch: it clears `purgeRequestedAt`, but refuses (409 `TENANT_PURGE_IN_PROGRESS`) once the worker stamped `purgeStartedAt` — including against a mid-request claim race. |
| `tests/tenant-purge-eligibility.test.ts`        | The purge worker only ever selects `archived` tenants: eligible when `archivedAt` is older than `TENANT_PURGE_RETENTION_DAYS` (default 30, `0` allowed, invalid values make the worker refuse to run), when `purgeRequestedAt` is set (retention override), or when `purgeStartedAt` is set (interrupted purge is always resumed). Non-archived tenants are never eligible regardless of markers. |
| `tests/tenant-purge-execution.test.ts`          | Purge order and crash-safety: the worker claims a tenant by stamping `purgeStartedAt` via a conditional update (a concurrent unarchive wins the race and the tenant is skipped), deletes R2 storage objects **before** any rows, then tenant-owned rows in explicit child-before-parent batches (users last), then the tenant row + `tenant.purged` completion event (with per-table row counts and storage object count) in one transaction. A storage failure aborts that tenant's row deletion but keeps it claimed for retry; re-runs are no-ops after success and resume after interruption without duplicate `tenant.purge_started` events. Other tenants' rows are never touched. |
| `tests/tenant-pilot-auto-archive.test.ts`       | Pilot auto-archive is opt-in (`TENANT_PILOT_AUTO_ARCHIVE_DAYS` unset → disabled; zero/garbage rejected): archives `pilot` tenants (only pilots) whose latest activity (sessions/visits/imports, floored at tenant `createdAt`) is older than the window, emitting `tenant.auto_archived`; conditional update closes the concurrent-upgrade race. |
| `tests/storage-tenant-object-purge.test.ts`     | `StorageService.deleteAllTenantObjects` deletes every live R2 object a tenant owns and marks each row `deleted` only after its remote delete succeeded — re-runs skip already-deleted rows, failures are counted (not marked) for retry, other tenants' objects untouched, and the id-cursor scan terminates in one pass even when every delete fails. |
| `tests/health-readiness.test.ts`                | Readiness and liveness behavior is explicit and preserves deployment health-check semantics.                                                        |
| `tests/json-logger.test.ts`                     | Structured logs preserve request and operational fields without leaking raw payload content.                                                        |
| `tests/sentry-service.test.ts`                  | Sentry integration behavior is controlled by configuration and error-reporting rules.                                                               |

## Track B-E coverage notes

Track B-E work is partly specified by this executable map and partly still requires product decisions.

- Track B, pilot data model completeness: existing tests cover current import template types, parsers, the first-pilot synthetic sample pack and validate-preview-confirm behavior. They do not yet define customer-specific sample packs.
- Track C, manager and admin workflows: existing tests cover user lifecycle, permissions and manager filters. Tenant-level settings are implemented, but future settings behavior still needs product decisions when adding new settings.
- Track D, AI reporting quality: existing tests cover strict schemas, AI job lifecycle, draft confirmation and manual fallback. They do not yet define quality thresholds, anonymized evaluation samples or weak-output scoring rules.
- Track E, commercial and pilot readiness: existing tests cover operations/readiness primitives. They do not yet define pilot success metrics, demo script acceptance or pilot-week support process.

When one of these notes says a behavior is not defined, the next agent must consult the matching spec in `docs/specs/` and ask the product owner for missing decisions before implementation.
