# Executable Specification

This document maps behavior tests in `tests/` to product and platform rules that are already implemented. Treat these tests as executable specification: when a future change touches the same behavior, read the matching test before editing code and update the test in the same change if the intended behavior changes.

Design documents explain intent. This file records behavior that has been pinned by tests.

## How to use this map

- Start with this file when a task affects tenant isolation, imports, AI reporting, manual fallback, permissions, manager filters, storage, operations, logging or readiness.
- Use the listed tests to understand exact edge cases before relying on higher-level roadmap wording.
- Do not weaken or remove a tested rule unless the product decision is documented in the relevant spec or reference document.
- When adding Track B-E behavior, add or update a focused test and add it to this map.

| `tests/request-origin.test.ts`                           | What the sign-in trail records about where a request came from, and why. The address is hashed with the same function `sessions.ipHash` uses — so the two join, and the trail supports "was this the same source" without becoming a list of addresses — and the forwarded chain is counted, because traffic through the web layer arrives with a characteristic length while a direct caller's does not. This exists for one reason: the plan accepts the "API is directly reachable" risk and names the sign-in trail as the thing that would show the traffic, and 3.5 shipped recording nothing that could. Ragged headers (empty entries, stray spaces) count correctly, and a request with no resolved address claims no source rather than inventing one. |
| `tests/auth-audit-events.test.ts`                        | Sign-in leaves a trail on both domains. A tenant login records `auth.login_succeeded`, and every refusal records `auth.login_failed` with the reason that tells `unknown_account`, `inactive_account` and `wrong_password` apart — including the address that matches no account, where the row carries `actorUserId: null`, `entityId: "unknown"` and the attempted address in `metadata`. Both failure paths write, so the trail cannot reintroduce the timing difference the response avoids. Sign-out resolves the account *before* the revocation that makes the session unfindable, and still clears the cookies when no live session matched. On the platform side the completed sign-in is recorded at the code step and never at the password step (a password alone yields no session), a wrong second factor is `reason: "wrong_code"` with the `method` used, and a platform row carries no `tenantId`. Both second-step routes are covered, not just the login one: enrolment ends in a session too, so a code rejected there records `reason: "wrong_code"` with `method: "enrollment"`, while an enrolment that fails for any other reason (a database error) records nothing — noise in this trail is worse than silence. A refused challenge — expired, replayed, or claimed for the other step — records `reason: "invalid_challenge"` on both routes with no account attached, since a token that did not resolve is the only identity the attempt had. The origin is recorded on the sign-out rows too, not only the sign-ins: the report reads every event type, so one written without it would sit in the "predates this" bucket forever and read as missing data rather than as a signed-out session. A failed audit write never breaks the sign-in it was recording — an unavailable audit table degrades the trail rather than refusing logins or answering a wrong password with a 500 — and is reported to Sentry as well as logged, since the symptom of a broken trail is an empty one. |

## Track B-E coverage notes

Track B-E work is partly specified by this executable map and partly still requires product decisions.

- Track B, pilot data model completeness: existing tests cover current import template types, parsers, the first-pilot synthetic sample pack and validate-preview-confirm behavior. They do not yet define customer-specific sample packs.
- Track C, manager and admin workflows: existing tests cover user lifecycle, permissions and manager filters. Tenant-level settings are implemented, but future settings behavior still needs product decisions when adding new settings.
- Track D, AI reporting quality: existing tests cover strict schemas, AI job lifecycle, draft confirmation and manual fallback. They do not yet define quality thresholds, anonymized evaluation samples or weak-output scoring rules.
- Track E, commercial and pilot readiness: existing tests cover operations/readiness primitives. They do not yet define pilot success metrics, demo script acceptance or pilot-week support process.

When one of these notes says a behavior is not defined, the next agent must consult the matching spec in `docs/specs/` and ask the product owner for missing decisions before implementation.
