# Executable Specification

This document maps behavior tests in `tests/` to product and platform rules that are already implemented. Treat these tests as executable specification: when a future change touches the same behavior, read the matching test before editing code and update the test in the same change if the intended behavior changes.

Design documents explain intent. This file records behavior that has been pinned by tests.

## How to use this map

- Start with this file when a task affects tenant isolation, imports, AI reporting, manual fallback, permissions, manager filters, storage, operations, logging or readiness.
- Use the listed tests to understand exact edge cases before relying on higher-level roadmap wording.
- Do not weaken or remove a tested rule unless the product decision is documented in the relevant spec or reference document.
- When adding Track B-E behavior, add or update a focused test and add it to this map.

| `tests/route-templates.test.ts`                          | Route templates are tenant-isolated and follow the same `routes.manage_team`/`routes.manage_own` ownership scope as route plans (shared `assertCanManageRouteForRepresentative` check). A representative can hold several plans on the same date — one per distinct template, enforced by the `route_plans_rep_date_template_key` partial unique index (see [data-model.md](data-model.md)) — so assigning a template to a date copies its items onto a new `RoutePlan` in sequence order and succeeds even if that representative already has a plan on that date from a *different* template; it only 409s if the *same* template is assigned to that date twice. Copying a month re-assigns each of the caller's own templated plans from the prior month onto the same day-of-month, skipping days that don't exist in the target month, that already have a plan from that same template, or that lose a race to a concurrent assign (a mid-batch conflict is counted as skipped, not raised) — a day already holding a *different* template's plan is not skipped — fetching each source day's occupied (date, template) set and referenced templates in one query apiece regardless of how many days are in the batch. A stop's `sequence` collision on create/update/move (two concurrent edits — including two overlapping moves computing the same temp slot — landing on the same position) 409s instead of raising an unhandled error, and assigning/copying is rejected if the template's representative is no longer an active field representative. Deleting a template writes its `route_template.deleted` audit event through the same transaction as the delete; the `ON DELETE SET NULL` cascade that unlinks the template's assigned plans can itself collide with `route_plans_rep_date_no_template_key` (the representative already holds a template-less manual plan on one of those dates), which surfaces as a 409 `ROUTE_TEMPLATE_DELETE_CONFLICT` instead of an unhandled 500. Moving a stop up/down runs the three-way temp-slot sequence swap inside one transaction and is a no-op (not an error) at either edge of the list; a full drag-and-drop reorder (`.../items/reorder`) generalizes the same temp-slot-then-final-sequence dance to N items in one transaction and 400s as `ROUTE_TEMPLATE_ITEM_REORDER_INVALID` unless the submitted `itemIds` is exactly a permutation of the template's current stops (right count, no duplicates, no foreign ids) — including the race where a stop is deleted by another session between that validation and the transaction itself (the update 404s at the DB level and is folded into the same 400 rather than an unhandled error); `GET /routes/templates` returns the same `page`/`pageSize`/`total` shape as `GET /routes`, and a single template can be read by id with the same ownership scope as the mutation endpoints. |

Logout is a real server-side revocation, not a cosmetic redirect — each logout spec captures the httpOnly session cookie first and proves that restoring it after sign-out no longer opens the console, including when the readable CSRF cookie was deleted before signing out (the PR #38/#39 fake-logout regression). |

## Track B-E coverage notes

Track B-E work is partly specified by this executable map and partly still requires product decisions.

- Track B, pilot data model completeness: existing tests cover current import template types, parsers, the first-pilot synthetic sample pack and validate-preview-confirm behavior. They do not yet define customer-specific sample packs.
- Track C, manager and admin workflows: existing tests cover user lifecycle, permissions and manager filters. Tenant-level settings are implemented, but future settings behavior still needs product decisions when adding new settings.
- Track D, AI reporting quality: existing tests cover strict schemas, AI job lifecycle, draft confirmation and manual fallback. They do not yet define quality thresholds, anonymized evaluation samples or weak-output scoring rules.
- Track E, commercial and pilot readiness: existing tests cover operations/readiness primitives. They do not yet define pilot success metrics, demo script acceptance or pilot-week support process.

When one of these notes says a behavior is not defined, the next agent must consult the matching spec in `docs/specs/` and ask the product owner for missing decisions before implementation.
