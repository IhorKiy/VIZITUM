# Environment Variables

Consolidated reference of environment variables actually read by the code. Sources of truth: `grep -rE "process\.env\." src apps/web scripts`, `.env.example`, `src/modules/storage/storage.config.ts`, `src/modules/health/health.service.ts`. For production values and naming see `docs/runbooks/production-env-checklist.md`. Never put secret values in docs or commits. Update this document in the same change as adding/removing an env var.

## API service (`src/`)

| Variable                                                               | Required            | Purpose                                                                                                                                                                                                                                                           |
| ---------------------------------------------------------------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`                                                         | yes                 | PostgreSQL connection string (Prisma). Also checked by `/health/readiness`.                                                                                                                                                                                       |
| `SESSION_SECRET`                                                       | yes (readiness)     | Checked by `/health/readiness` as a critical var. Session tokens themselves are random and hashed, so this is a deployment guard, not a signing key.                                                                                                              |
| `PORT` / `HOST`                                                        | no                  | API listen port/host; defaults `4000` / `0.0.0.0`.                                                                                                                                                                                                                |
| `NODE_ENV`                                                             | no                  | `production` prefixes the session and CSRF cookie names with `__Host-` (`src/common/cookie-naming.ts`) — it no longer drives the `Secure` flag; see `COOKIE_SECURE`. |
| `COOKIE_SECURE`                                                        | **yes in production** | Drives the session/CSRF cookies' `Secure` flag directly (`src/modules/auth/auth.constants.ts`), rather than inferring it from `NODE_ENV`. Production once ran with `NODE_ENV` unset, which silently sent the session cookie without `Secure`; this closes that specific misconfiguration by making the flag its own explicit, required setting. Must be exactly `"true"` (trimmed) — anything else, including unset, refuses to start in production. Unset locally, where cookies are sent over plain HTTP. |
| `SESSION_COOKIE_NAME`                                                  | no                  | Dev-only override for the tenant session cookie's name (`src/modules/auth/auth.constants.ts`), so parallel worktree dev sessions on different ports don't clobber each other's cookie — browsers share cookies across localhost ports regardless of which dev server set them. Ignored in production, which always uses the `__Host-`-prefixed name. `apps/web` reads the *same* variable from its own environment (`apps/web/lib/api-client.ts`) to clear the right cookie on logout — set it identically in `.env` and `apps/web/.env.local` for a given worktree slot. The CSRF cookie has no equivalent override; no worktree slot varies it today. |
| `REDIS_URL`                                                            | **yes in production** | Backs the auth rate-limit counters (`@nestjs/throttler` storage plus the per-account failed-login counters). Unset, they live in this process's memory: they reset on every deploy and are not shared between instances, so production refuses to start without it. Local dev, tests and e2e use the memory path. |
| `TOTP_ENCRYPTION_KEY`                                                  | **yes in production** | Encrypts the platform owner's TOTP secret and any pending enrolment secret at rest (AES-256-GCM, `src/common/secret-box.ts`). 32 bytes, base64 or hex — `openssl rand -base64 32`. A TOTP secret cannot be hashed the way a password is, because verifying a code needs the secret itself, so without this any database read — a dump, a replica, a restore drill — hands over a permanent code generator for the one account that reaches every tenant's data. Production refuses to start without a valid key; a key of the wrong length throws rather than being padded, so nobody ends up with an encryption they believe is 256-bit. Where it is unset (local dev, tests) secrets are written in the clear exactly as before and both forms are readable, which is what lets an already-enrolled owner sign in through the deploy that turns encryption on: that row is re-encrypted on their next sign-in, and `npm run encrypt:totp-secrets` migrates every row at once without waiting for one. **Losing or rotating this key makes existing secrets undecryptable** — the owner then signs in with a recovery code and re-enrols, so keep it with the same care as the database credentials, and do not rotate it casually. |
| `TRUST_PROXY_HOPS`                                                     | **yes in production** | Number of reverse proxies in front of the API (`src/common/trust-proxy.ts`), passed to Express `trust proxy`. Deliberately a hop count, not `true`: `true` trusts the whole forwarded chain, and since clients can send `X-Forwarded-For` themselves it would let anyone choose the address they are limited under. Any non-integer value (including `true`) throws at boot rather than degrading silently, and production refuses to start without it at all — there is no safe default. Too low and `request.ip` is an infrastructure address, so all traffic shares one rate-limit bucket and the `ipHash` on every session is identical; too high and the value is client-controlled. `0` for a local dev server. **There is no value to copy for a deployment — measure it.** The count is however many proxies actually sit in front of that particular API, and it is easy to under-count: reasoning from the application's own topology (the web layer forwards the originating client address via `buildRequestHeaders` in `apps/web/lib/api-client.ts`, the hosting edge appends the Next server's) gives 2, but staging measured **3**, because a Cloudflare proxy sits in front of Render and contributes a hop nothing in this repository knows about. Measure each environment separately. `GET /health/readiness`, called with the platform operations bearer token, returns `checks.authHardening.proxyResolution` with the address the setting actually resolved for that request and the length of its forwarded chain; the correct hop count is that length. Note what the correct value buys and what it does not: at chain length the leftmost entry is authoritative, so whoever wrote that entry chooses the address they are limited under. **An edge that merely *appends* to `X-Forwarded-For` — which is what Cloudflare does — does not make it safe; only one that overwrites or strips the inbound header does.** That is why the address the API keys on is not taken from the chain at all: `CLIENT_IP_HEADER` (below) names a header the edge overwrites, and `apps/web/lib/api-client.ts` forwards that single value as the only entry. Where neither holds — an API reachable directly, or a deployment that cannot name such a header — the per-IP limits are advisory and the per-account backoff is the control that still applies. The API being directly reachable is the case today and is an accepted risk, not an oversight: `docs/security-remediation-plan.md` records the decision, why blocking it is unavailable on the current hosting, and the fix when it is reopened. |
| `RATE_LIMIT_DISABLED`                                                  | no                  | `true` switches off every auth rate limit and the per-account backoff. Only `apps/web/playwright.config.ts` sets it — the suite drives many parallel logins from one loopback address. Production refuses to start with it enabled. |
| `OPENAI_API_KEY`                                                       | for AI flows        | OpenAI auth for transcription/extraction. Manual report confirmation must keep working without it.                                                                                                                                                                |
| `OPENAI_TRANSCRIPTION_MODEL` / `OPENAI_EXTRACTION_MODEL`               | no                  | Model overrides for AI jobs (defaults in `src/modules/ai`).                                                                                                                                                                                                       |
| `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | yes (storage flows) | S3-compatible storage (Cloudflare R2 in staging). Missing values throw at first storage use.                                                                                                                                                                      |
| `S3_REGION`                                                            | no                  | Default `auto`.                                                                                                                                                                                                                                                   |
| `S3_FORCE_PATH_STYLE`                                                  | no                  | Boolean, default `true`.                                                                                                                                                                                                                                          |
| `EMAIL_PROVIDER`                                                       | no                  | Invite email driver (`src/modules/email`): `off` (default — invites created without email, link shared manually), `console` (dev-only: logs the full email incl. accept link), `resend` (Resend HTTP API). Email is best-effort: a failure never blocks invite creation; the outcome lands on `Invite.emailStatus`. |
| `EMAIL_FROM`                                                           | `resend` provider   | From address/header for outgoing email, e.g. `Vizitum <no-reply@vizitum.app>`. The domain must be verified in Resend.                                                                                                                                             |
| `RESEND_API_KEY`                                                       | `resend` provider   | Resend API key.                                                                                                                                                                                                                                                   |
| `APP_BASE_URL`                                                         | when email enabled  | Public web app origin used to build absolute invite accept links in emails (`{APP_BASE_URL}/{tenantSlug}/invites/accept?...`). Read only here (`src/modules/email/email.config.ts`) — the web app never reads it. In production it is `https://www.vizitum.com`, never the deployment's own `*.vercel.app` alias: this value is baked into mail that outlives any later domain change. `apps/web/lib/canonical-host.ts` forwards the alias to the canonical origin so links already sent still land correctly, but that is a backstop, not a substitute for setting this. |
| `TURNSTILE_SECRET_KEY`                                                 | **yes in production** | Cloudflare Turnstile secret. When set, `POST /auth/login` and `POST /platform/auth/login` require a valid `captchaToken` verified against Cloudflare's siteverify endpoint (`src/modules/auth/turnstile.service.ts`); rejection is `400 CAPTCHA_INVALID`. Unset disables the captcha entirely — fine for local dev, tests and e2e, which is why production **refuses to start without it** (`src/modules/auth/security-config.ts`): a silent no-op is the failure mode worth failing loudly on. A siteverify response that is not 2xx, or a 2xx that is not the documented JSON, is a verification failure (fails closed). Only a genuine transport failure fails open, behind a 3s deadline and a 30s circuit breaker. Set together with the web app's `TURNSTILE_SITE_KEY`. |
| `PLATFORM_OPERATIONS_TOKEN_SHA256`                                     | recommended         | SHA-256 hash of the platform operations bearer token (preferred over plaintext). Grants only `platform.operations.read`, which reaches two things: `GET /operations/summary`, and the operator-only `checks.authHardening.proxyResolution` block of `GET /health/readiness` (the readiness route itself stays anonymous — only that block is gated). It cannot manage tenants (that needs a `platform_owner` session — see [permissions.md](permissions.md)). With neither this nor the plaintext var set, the token can never match, so the proxy diagnostic is simply absent — indistinguishable from a rejected token, since spelling out which of the two it was would turn an anonymous endpoint into a token-validity oracle. |
| `PLATFORM_OPERATIONS_TOKEN`                                            | fallback            | Plaintext operations token; used only when the SHA256 var is unset. Same scope as above.                                                                                                                                                                          |
| `SENTRY_DSN`, `SENTRY_ENVIRONMENT`, `SENTRY_RELEASE`                   | no                  | Error reporting for 5xx responses and failed worker runs; disabled when DSN is empty.                                                                                                                                                                             |

## Worker (`src/worker.ts`)

Same env as the API (it boots the same Nest application context: `DATABASE_URL`, `S3_*`, Sentry vars), plus:

| Variable                         | Required          | Purpose                                                                                                                                                                                                                                               |
| -------------------------------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WORKER_TASK`                    | no                | Task selector: `cleanup` (default — expired AI jobs + temporary storage objects) or `purge` (tenant lifecycle: auto-archive stale pilots, purge archived tenants past retention).                                                                     |
| `TENANT_PURGE_RETENTION_DAYS`    | no (`purge` task) | Days an archived tenant is kept before the purge worker may delete it (default `30`; `0` = eligible immediately). Anything that is not a non-negative integer makes the worker refuse to run — it never falls back to a default for destructive work. |
| `TENANT_PILOT_AUTO_ARCHIVE_DAYS` | no (`purge` task) | Opt-in: archive `pilot` tenants with no activity (sessions/visits/imports, floored at tenant creation) for this many days. **Disabled when unset.** Must be a positive integer; `0` and garbage are rejected.                                         |

## Web service (`apps/web`)

| Variable                                                    | Required       | Purpose                                                                                                                        |
| ----------------------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `API_BASE_URL`                                              | yes in deploys | Backend base URL **including `/api`** (default `http://127.0.0.1:4000/api`), used server-side in `apps/web/lib/api-client.ts`. |
| `SESSION_COOKIE_NAME`                                       | no             | Same dev-only override as the API's own `SESSION_COOKIE_NAME` (`apps/web/lib/api-client.ts`) — read from this workspace's own environment, since server actions run in a separate process from the API. Must match the API's value for a given worktree slot so logout clears the cookie the API actually set. Ignored in production. |
| `CLIENT_IP_HEADER`                                          | **yes in production** | Name of the request header carrying the originating client's address (`apps/web/lib/client-address.ts`). Every API call from this layer is server-to-server, so the address forwarded here becomes the identity the API's per-IP rate limits key on. **Set it to a header the host writes and refuses to take from the client. `apps/web` runs on Vercel, so that is `x-vercel-forwarded-for`** — identical to `x-forwarded-for` today, but the one Vercel keeps authoritative if a proxy is ever put on top. Use `cf-connecting-ip` only where Cloudflare's proxy actually terminates the request: it does **not** for `www.vizitum.com`, which is DNS-only on Cloudflare and served by Vercel directly (verified by response headers — `server: Vercel`, no `cf-ray`), so setting it there would forward no address at all and put every caller in one bucket. Do not set it to `x-forwarded-for`: whether that one is forgeable is a property of the host rather than of this app — Vercel overwrites it and drops external values to prevent spoofing, while Cloudflare *appends* to a client-supplied one, leaving the caller's own entry leftmost. When the configured header is absent from a request, no address is forwarded and the API keys on this layer's own — over-limiting rather than handing out free buckets. Unset, the production process refuses to start (`register()` in `apps/web/instrumentation.ts`); development, tests and e2e need nothing, since with no proxy in front there is nothing to forge through and the forwarded headers are honoured as before. **Vercel preview deployments are exempt** even though they run with `NODE_ENV=production` — the gate reads `VERCEL_ENV` and only fires on `production` (or when `VERCEL_ENV` is absent, i.e. off Vercel). A preview serves no real traffic, so it forwards no address and shares one bucket; gating it would refuse every preview branch *invisibly*, since `next build` does not evaluate the hook and the deployment reports itself complete. Setting the variable for the Preview environment too is still worth doing if you want previews keyed per client, but nothing breaks without it. |
| `TURNSTILE_SITE_KEY`                                        | no             | Cloudflare Turnstile site key. When set, both login pages render the Turnstile widget (`apps/web/components/turnstile-widget.tsx`) and forward its token to the API. Read server-side per request (not `NEXT_PUBLIC_*`), so no rebuild is needed to change it. Set together with the API's `TURNSTILE_SECRET_KEY` — a site key without the secret shows a widget the API ignores; the secret without a site key locks logins out. |
| `ENABLE_DEMO_FALLBACK` / `NEXT_PUBLIC_ENABLE_DEMO_FALLBACK` | no             | Enable demo data fallback (`apps/web/lib/demo-mode.ts`); keep disabled in production.                                          |
| `NEXT_PUBLIC_SENTRY_DSN`, `NEXT_PUBLIC_SENTRY_ENVIRONMENT`, `NEXT_PUBLIC_SENTRY_RELEASE` | no | Web error reporting (`apps/web/lib/error-reporting.ts`): browser errors (`window.onerror`/unhandled rejections, `global-error.tsx`) and Next server-side request errors (`apps/web/instrumentation.ts`). The DSN is public by design (it ships in the browser bundle); may be the same Sentry project as the API's or a separate one. Disabled when unset. Baked in at build time — a change requires a rebuild. |
| `NEXT_PUBLIC_ENABLE_SERVICE_WORKER`                         | no             | Registers `apps/web/public/sw.js` in a non-production `next dev` session (`apps/web/components/service-worker-registration.tsx`), which otherwise skips registering there — dev's `/_next/static/` chunks aren't immutable by URL the way a production build's are, so the worker's cache-first strategy risks serving a stale one. Set only by `apps/web/playwright.config.ts`'s own web server, for `field-offline-shell.spec.ts` to exercise the real worker; in production the worker always registers regardless of this flag. |

Set these when the seeded owner uses non-default credentials.                                                                                                                                                             |
| `API_READINESS_URL`, `DATABASE_URL`                                                                                                                                           | `scripts/restore-drill-check.sh` (`npm run restore:drill:check`)  | Restore drill validation.                                                                                                                                                                                                                                                                                                             |
