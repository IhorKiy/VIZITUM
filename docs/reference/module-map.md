# Module Map

Reference for the implemented codebase. Source of truth: `src/modules/*`, `src/app.module.ts`, `src/main.ts`, `src/worker.ts`, `apps/web/app/**`, `apps/web/lib/*`. This describes the current state, not design intent — for design rationale see `docs/vizitum-low-level-technical-design.md`.

When you change a module's responsibility, routes, or key files, update this document in the same change.

## Backend entrypoints

- `src/main.ts` — API server. Applies request-id middleware, access log, CSRF protection, sets global prefix **`/api`**, installs `ApiErrorFilter`. Listens on `HOST`/`PORT` (default `0.0.0.0:4000`).
- `src/worker.ts` — run-to-completion worker process. `WORKER_TASK` selects the task: `cleanup` (deletes expired failed AI jobs and expired temporary storage objects) or `purge` (tenant lifecycle: auto-archives stale `pilot` tenants when `TENANT_PILOT_AUTO_ARCHIVE_DAYS` is set, then permanently deletes archived tenants past `TENANT_PURGE_RETENTION_DAYS` or explicitly marked for purge — `TenantPurgeService`, storage objects first, then rows in explicit dependency order, then the tenant row). Runs to completion and exits. Deployed as a cron, not a long-running queue consumer. (The former `provision` task was removed when tenant creation stopped using `draft`/`provisioning` — see the `platform` module entry below.)
- `src/common/` — `request-id.middleware.ts`, `access-log.middleware.ts`, `api-error.filter.ts` (global error envelope), `json-logger.service.ts`, `sentry.service.ts`, `normalize.ts` (shared `normalizeEmail`), `phone.ts` (shared phone handling: `normalizePhoneInput` parses input to E.164 against the tenant's `phoneCountry` — `+`-prefixed input is any-country international — and `formatPhoneForDisplay` renders stored E.164 nationally/internationally; mirrored web-side in `apps/web/lib/phone.ts`, consumed by the shared `components/phone-input.tsx` input), `cookie-token.ts` (cookie name-parameterized read/write/clear, used by both tenant and platform session cookies, and by the CSRF cookie reader), `session-lifecycle.ts` (shared token issuance + TTL/`revokedAt` activity check, used by both tenant and platform sessions, and by `PermissionGuard`'s platform-session branch), `time.ts` (`MILLISECONDS_PER_DAY`, the single source for every day-based TTL calculation).

Note: Redis/BullMQ appear in the LLD and `.env.example`, but no backend code currently consumes `REDIS_URL`. AI transcription/extraction jobs execute in the API process; the worker is a cron cleanup task.

### Tenancy invariant (load-bearing)

Every module touching tenant-owned data reads `tenantId` from `RequestContext` (`request.context`), which `PermissionGuard` builds from the session. Never trust a `tenantId` from a request body, param, or query. Controllers use a local `getRequestContext(request)` helper that throws if the guard did not run.

## Frontend (`apps/web`)

Next.js App Router. All product screens live under the tenant slug: `apps/web/app/[tenantSlug]/...`. Navigation is filtered by session permissions and grouped into role zones (below).

**i18n (next-intl, without i18n routing)**: the UI locale is the tenant's `language` setting (`en`/`uk`), not the URL or browser. `proxy.ts` forwards the pathname; `i18n/request.ts` extracts the tenant slug and resolves the locale via the public `GET /tenants/:slug/locale` endpoint (so pre-auth login/invite pages are localized too; the same response also carries the tenant's `phoneCountry`, which server components pass down to `components/phone-input.tsx` and phone display formatting). Dictionaries live in `apps/web/messages/{en,uk}.json` (namespaces: `common`, `auth`, `invites`, `field`, `manager`, `admin`, `operations`); `en` is canonical and deep-merged under other locales so missing keys fall back to English. `platform/*` pages always render in `en`; the marketing landing (`/` in `uk`, `/en` in `en` — see the route table) is the one exception to the request-scoped locale — it pins its dictionary via a direct import (public marketing page, no tenant to resolve a locale from; `en` is also in `NON_TENANT_SEGMENTS` so the `/en` route skips the tenant locale lookup). Every new user-visible string goes through the dictionary — no hardcoded UI literals in `apps/web/app/**` or `components/`. Deeply-scoped translators with flat leaf keys (e.g. `getTranslations("common.zone.names")` then `t(zone)`, not `getTranslations("common")` then `t("zone.names.field")`) are required, not just style — next-intl's typed message keys fail to type-check 3+ segment relative paths in this project's TS setup.

### Role zones

Nav items are grouped into four zones — `field`, `manager`, `admin`, `operations` — one per top-level route prefix (`field-*` areas → `field`, `admin-*` → `admin`, `manager-*` → `manager`, `operations` → `operations`). `apps/web/lib/navigation.ts` is the single source of truth: each nav item definition carries its `zone` alongside the `requiredPermissions` it already had; `availableZones(permissions, productsEnabled)` derives which zones a user has (a zone is available when any of its items' `requiredPermissions` are met — reuses the same filter `buildTenantNav` uses, not a parallel mapping), `resolveDefaultZone` picks the stored-zone-if-still-available/only-zone/none-of-the-above outcome, and `resolveZoneLanding` combines both into the one landing decision (`zone` / `choose` / `no-access`) shared by the login redirect, the tenant-home redirect (`[tenantSlug]/page.tsx`) and the `AppShell` deep-link guard.

`AppShell` (`components/app-shell.tsx`) fetches the session once per page and: (1) redirects an authenticated user off a zone their permissions don't cover, using the same `resolveZoneLanding` order — unauthenticated requests are left untouched, since every zone page already has its own signed-out fallback UI/demo mode and there was no pre-existing redirect-to-login to preserve; (2) renders only the active zone's nav items (previously all zones were mixed in one flat list); (3) renders a compact switcher (sidebar footer + mobile topbar) linking to the user's other available zones when there is more than one. There are no per-zone `layout.tsx` files — every page still calls `AppShell` directly, so the guard lives there instead of being duplicated per page.

Persisting a zone choice (`User.lastSelectedZone`, see [data-model.md](data-model.md)) goes through the shared server action `apps/web/lib/zone-actions.ts` (`selectZoneAction`), used identically by the `/choose-zone` chooser and the `AppShell` switcher, which calls `POST /auth/zone` (see [api-reference.md](api-reference.md)) and redirects regardless of whether the persist succeeded — a rejected zone just means the landing page's own `AppShell` guard re-resolves and corrects.

**Known cross-zone overlap**: because zone availability reuses each nav item's existing `requiredPermissions` verbatim (as required — zones must never be derived from role names), a plain `team_manager` has both `field` and `manager` available, not just `manager`: `routes.read` (shared with `field_representative`) makes `field-planning` visible, and `visits.read_team` makes the field overview visible. That overlap is intentional — those are real field-zone permissions a manager holds — so a single-role `team_manager` sees the zone chooser on first login.

The corollary is that a permission shared across roles must never be the *only* gate on a zone's item, or the whole zone leaks. Two items are deliberately gated more narrowly than the endpoint they open for exactly this reason: `admin-pilot` on `tenant.settings.read` rather than `pilot_review.read` (also held by `team_manager` — it previously handed plain managers the entire admin zone), and `manager-potential` on `dashboard.manager.read` rather than `location_insights.read` (also held by field reps and admins). Neither costs a role the screen was meant for — the intended audience holds the narrower permission too. (For `admin-pilot` a `team_manager` does lose access, deliberately: the section is admin configuration work. `manager-potential` loses nobody, since every `team_manager` holds both permissions.) `tests/nav-zones.test.ts` and `tests/zone-permission-mirror.test.ts` pin that a `team_manager`-only permission set yields `field` + `manager` and never `admin`.

### Shared frontend libs (`apps/web/lib/`)

- `api-client.ts` — the only path to the backend. Server-side fetch helpers (`apiGet/apiPost/apiPatch/apiDelete`) that forward the incoming cookie header, `x-request-id`, and the CSRF token, sent as `x-csrf-token`. `buildRequestHeaders(path)` picks `vizitum_platform_csrf` for `/platform/*` paths and `vizitum_csrf` otherwise, matching the backend's per-domain CSRF cookie (see `src/modules/auth/csrf.ts`) — a request built for the wrong domain sends a token that won't match either cookie. Returns `ApiResult<T> = { ok: true; data } | { ok: false; status; message }` — screens branch on `ok`, they do not throw. Also holds the frontend response types. Base URL: `API_BASE_URL` env (default `http://127.0.0.1:4000/api`).
- `navigation.ts` — `buildTenantNav(tenantSlug, permissions)` returns nav items filtered by required permissions (a nav item shows if the user has _any_ of its `requiredPermissions`) and tagged with a `zone`. Add new screens here with their permission requirements and zone. Also exports the zone helpers described above: `availableZones`, `resolveDefaultZone`, `zoneHomePath`, `resolveZoneLanding` — all pure (no fetch calls), unit-tested directly from `tests/nav-zones.test.ts`.
- `back-navigation.ts` — where a `BackLink` points. A screen with several entry points can't hardcode one destination, so the linking screen appends its own tenant-relative location as `?from=` (`backOrigin(path, filters)` + `withBackOrigin(href, origin)`) and the target resolves it (`resolveBackTarget(tenantSlug, from, fallback)`), falling back to the hierarchical parent for deep links. `from` is matched against the `RETURNABLE_SCREENS` allowlist, which both rejects an off-site/cross-tenant/unlisted value and supplies the `common.back.*` label — so the control always announces the screen it really lands on; it must additionally share a zone with the `fallback` (read off the fallback href), since the allowlist is global and no real journey crosses zones. Origins nest (locations list → card → visit history → report), bounded by a 2048-character cap sized for a full-length Cyrillic `search` filter carried three levels deep — each level re-encodes the one below it, so that case runs to ~1500 characters. Pure and framework-free, unit-tested from `tests/web-back-navigation.test.ts`.
- `zone-actions.ts` — `selectZoneAction`, the shared `"use server"` action that persists a zone pick (`POST /auth/zone`) and redirects; used by both the chooser and the `AppShell` switcher. The form-supplied tenant slug is shape-checked (`isTenantSlug` from `tenant-locale.ts`) before being interpolated into the redirect path, so a crafted value can't turn the redirect cross-origin.
- `backend-cookies.ts` — cookie forwarding helpers for server components.
- `demo-mode.ts` — demo data fallback, controlled by `ENABLE_DEMO_FALLBACK` / `NEXT_PUBLIC_ENABLE_DEMO_FALLBACK`; disabled by default in production.
- `tenant-locale.ts` — supported locales (`en`, `uk`), tenant-slug extraction from the pathname and the locale/timezone lookup against `GET /tenants/:slug/locale` (fail-open to `en`/UTC).
- `branding.ts` — the four tenant color presets as CSS-variable maps (`--accent*`, `--sidebar-*`; scheme ids mirrored against `src/modules/settings/branding.ts` by `tests/branding-scheme-mirror.test.ts`), `buildSchemeStyle` (emits the `:root` override block; the default `emerald` emits nothing) and the picker swatches.
- `tenant-branding.ts` — `resolveTenantBranding(slug)`: branding lookup against `GET /tenants/:slug/branding`, fail-open to emerald/no-logo, wrapped in React `cache()` so the tenant layout, `AppShell` and login page share one fetch per request. Rendered into the page by `app/[tenantSlug]/layout.tsx` — a deliberate, chrome-free exception to the "no per-zone layouts" convention that only injects the `:root` CSS-variable override (and by `BrandMark` in `components/brand-mark.tsx`, which shows the uploaded logo or the default "V" glyph).
- `format.ts` — locale-aware date/enum formatting helpers: `formatDateTime`/`formatShortDate` take a next-intl formatter (honors the tenant timezone), `formatEnumLabel` translates enum-like values via `common.labels.*` with a humanized fallback.
