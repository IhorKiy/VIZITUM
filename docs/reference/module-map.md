# Module Map

Reference for the implemented codebase. Source of truth: `src/modules/*`, `src/app.module.ts`, `src/main.ts`, `src/worker.ts`, `apps/web/app/**`, `apps/web/lib/*`. This describes the current state, not design intent — for design rationale see `docs/vizitum-low-level-technical-design.md`.

When you change a module's responsibility, routes, or key files, update this document in the same change.

## Backend entrypoints

- `src/main.ts` — API server. Applies request-id middleware, access log, CSRF protection, sets global prefix **`/api`**, installs `ApiErrorFilter`. Listens on `HOST`/`PORT` (default `0.0.0.0:4000`).
- `src/worker.ts` — run-to-completion worker process. `WORKER_TASK` selects the task: `cleanup` (deletes expired failed AI jobs and expired temporary storage objects) or `purge` (tenant lifecycle: auto-archives stale `pilot` tenants when `TENANT_PILOT_AUTO_ARCHIVE_DAYS` is set, then permanently deletes archived tenants past `TENANT_PURGE_RETENTION_DAYS` or explicitly marked for purge — `TenantPurgeService`, storage objects first, then rows in explicit dependency order, then the tenant row). Runs to completion and exits; a failed run is reported to Sentry (same `SENTRY_*` vars as the API, tagged `module: worker`) before the exit code is set. Deployed as a cron, not a long-running queue consumer. (The former `provision` task was removed when tenant creation stopped using `draft`/`provisioning` — see the `platform` module entry below.)
- `src/common/` — `request-id.middleware.ts`, `access-log.middleware.ts`, `api-error.filter.ts` (global error envelope), `json-logger.service.ts`, `sentry.service.ts`, `normalize.ts` (shared `normalizeEmail`), `phone.ts` (shared phone handling: `normalizePhoneInput` parses input to E.164 against the tenant's `phoneCountry` — `+`-prefixed input is any-country international — and `formatPhoneForDisplay` renders stored E.164 nationally/internationally; mirrored web-side in `apps/web/lib/phone.ts`, consumed by the shared `components/phone-input.tsx` input), `cookie-token.ts` (cookie name-parameterized read/write/clear, used by both tenant and platform session cookies, and by the CSRF cookie reader), `session-lifecycle.ts` (shared token issuance + TTL/`revokedAt` activity check, used by both tenant and platform sessions, and by `PermissionGuard`'s platform-session branch), `time.ts` (`MILLISECONDS_PER_DAY`, the single source for every day-based TTL calculation).

Note: Redis/BullMQ appear in the LLD and `.env.example`, but no backend code currently consumes `REDIS_URL`. AI transcription/extraction jobs execute in the API process; the worker is a cron cleanup task.

### Tenancy invariant (load-bearing)

Every module touching tenant-owned data reads `tenantId` from `RequestContext` (`request.context`), which `PermissionGuard` builds from the session. Never trust a `tenantId` from a request body, param, or query. Controllers use a local `getRequestContext(request)` helper that throws if the guard did not run.

## Frontend (`apps/web`)

Next.js App Router. All product screens live under the tenant slug: `apps/web/app/[tenantSlug]/...`. Navigation is filtered by session permissions and grouped into role zones (below).

**CSV exports**: `apps/web/lib/csv.ts` is the one place a CSV cell is written web-side (`toCsv`/`escapeCsvCell`), used by the manager dashboard's export. Beyond the ordinary quoting it prefixes a value that starts with `=`, `+`, `@`, tab or carriage return with `'`, because a spreadsheet evaluates such a cell as a formula and the export is built from tenant-entered names; a value that parses as a plain number is left alone so negative numbers survive the round trip. `escapeCsvCell` in `src/modules/imports/imports.service.ts` (import templates) applies the same two rules — a deliberate mirror, like `phone.ts`, pinned by `tests/csv-formula-injection.test.ts`.

**Security headers**: the fixed ones (HSTS, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`) are static entries in `next.config.ts`. The Content-Security-Policy cannot be, because it carries a per-request nonce, so it is built in `apps/web/lib/content-security-policy.ts` and set by `proxy.ts` — which means **the proxy's `matcher` decides which pages have a CSP at all**. It excludes `_next` and paths ending in a static file extension (so `public/offline.html`, whose hand-written inline `<script>` can never carry a nonce, and `sw.js` stay out). It deliberately does **not** exclude "any path containing a dot", the shape most Next examples use: `[tenantSlug]` accepts any string and the session cookie decides what is served, so `/acme.x/field` rendered the real authenticated app with no policy and no nonce. `tests/web-csp-matcher.test.ts` pins both halves.

**Tenant slug shape**: `apps/web/app/[tenantSlug]/layout.tsx` rejects a segment that is not slug-shaped with `notFound()`, using `normalizeTenantSlug` (`lib/tenant-locale.ts`) — trim-and-lowercase, mirroring the API's `normalizeSlug`, then `isTenantSlug`. Nothing constrained that segment before, and what is served under it is decided by the session cookie rather than by the slug, so any string rendered the real authenticated app: `/team.html` arrived with **no Content-Security-Policy** (a path ending in a known extension is skipped by the proxy matcher, which cannot tell it from `sw.js`), and the same unchecked value fed the `redirect()` targets pages build from it. This is the rule the rest of the frontend already applies — the workspace entry screen, the remembered workspace and the zone actions all gate on `isTenantSlug`; the layout was the one door without it. `/platform`, `/en` and `/sign-in` are static routes that shadow the dynamic segment, so they never reach it.

**Canonical host**: the production deployment answers on its Vercel alias as well as on the domain the product owns, so `proxy.ts` redirects requests that arrive on the alias (or the apex) to the origin named by `apps/web/lib/site.ts` — the same origin the marketing pages advertise as canonical. The decision is `apps/web/lib/canonical-host.ts`, deliberately an exact-hostname allowlist rather than a `*.vercel.app` pattern, so preview deployments keep serving themselves; `localhost`/`127.0.0.1` are untouched, which is what keeps dev and the Playwright e2e run working. It is a 307, not a 308: a permanent redirect is cached for the life of a browser profile and would strand everyone on the alias if the custom domain ever had to be bypassed. 307 also keeps the request method where a 302 would not — a server action posting to the alias is replayed as a POST rather than arriving as a GET the route cannot answer — though that replay is still refused: it is cross-origin, so the browser sends `Origin: null` and Next's server action origin check rejects it. The gain is a visible failure rather than a silent downgrade, not a working cross-host post. This exists because not every link into the app is built here — invite emails are composed by the API from `APP_BASE_URL` (see [environment.md](environment.md)), and mail already sent cannot be corrected by fixing that variable.

**i18n (next-intl, without i18n routing)**: the UI locale is the tenant's `language` setting (`en`/`uk`), not the URL or browser. `proxy.ts` forwards the pathname; `i18n/request.ts` extracts the tenant slug and resolves the locale via the public `GET /tenants/:slug/locale` endpoint (so pre-auth login/invite pages are localized too; the same response also carries the tenant's `phoneCountry`, which server components pass down to `components/phone-input.tsx` and phone display formatting). Dictionaries live in `apps/web/messages/{en,uk}.json` (namespaces: `common`, `auth`, `passwordReset`, `account`, `invites`, `field`, `manager`, `admin`, `operations`); `en` is canonical and deep-merged under other locales so missing keys fall back to English. `platform/*` pages always render in `en`; the marketing landing (`/` in `uk`, `/en` in `en` — see the route table) is the one exception to the request-scoped locale — it pins its dictionary via a direct import (public marketing page, no tenant to resolve a locale from; `en` is also in `NON_TENANT_SEGMENTS` so the `/en` route skips the tenant locale lookup). Every new user-visible string goes through the dictionary — no hardcoded UI literals in `apps/web/app/**` or `components/`. Deeply-scoped translators with flat leaf keys (e.g. `getTranslations("common.zone.names")` then `t(zone)`, not `getTranslations("common")` then `t("zone.names.field")`) are required, not just style — next-intl's typed message keys fail to type-check 3+ segment relative paths in this project's TS setup.

### Role zones

Nav items are grouped into four zones — `field`, `manager`, `admin`, `operations` — one per top-level route prefix (`field-*` areas → `field`, `admin-*` → `admin`, `manager-*` → `manager`, `operations` → `operations`). `apps/web/lib/navigation.ts` is the single source of truth: each nav item definition carries its `zone` alongside the `requiredPermissions` it already had; `availableZones(permissions, productsEnabled)` derives which zones a user has (a zone is available when any of its items' `requiredPermissions` are met — reuses the same filter `buildTenantNav` uses, not a parallel mapping), `resolveDefaultZone` picks the stored-zone-if-still-available/only-zone/none-of-the-above outcome, and `resolveZoneLanding` combines both into the one landing decision (`zone` / `choose` / `no-access`) shared by the login redirect, the tenant-home redirect (`[tenantSlug]/page.tsx`) and the `AppShell` deep-link guard.

`AppShell` (`components/app-shell.tsx`) fetches the session once per page and: (1) redirects an authenticated user off a zone their permissions don't cover, using the same `resolveZoneLanding` order — unauthenticated requests are left untouched, since every zone page already has its own signed-out fallback UI/demo mode and there was no pre-existing redirect-to-login to preserve; (2) renders only the active zone's nav items (previously all zones were mixed in one flat list), each optionally carrying a count badge — tasks still in progress on `field-tasks`, unacknowledged announcements on `field` — both fetched in the shell's own `Promise.all` and only for the field zone; (3) renders a compact switcher (sidebar footer + mobile topbar) linking to the user's other available zones when there is more than one. There are no per-zone `layout.tsx` files — every page still calls `AppShell` directly, so the guard lives there instead of being duplicated per page.

**The field menu** (`components/field-menu.tsx`) is the field zone's only topbar control, and it replaces that zone's mobile zone switcher (the drawer holds the switcher instead). The bottom nav keeps the four screens a working day is made of (today's route, planning, tasks, history); the reusable routes, the catalogue screens, help and the session controls live behind the menu button — a native `<dialog>` drawer, for its focus trap, Esc-to-close and `::backdrop` scrim. `/field/announcements` is there because the home screen now carries only the *unread* notices: once a notice is acknowledged it has done its job, and the menu is where a rep goes back to a standing rule they already read. `/field/routes` is there because building a round is setup rather than day-of work — written once, then reused, while "which route runs today" is the calendar's question — and because at 375px a fifth slot already cost `field-planning` its full label. That move is free for zone availability only because `/field/planning` is gated on the same `routes.read`, so the field zone's permission union is unchanged (pinned in `tests/nav-zones.test.ts`). Its entries come from `buildFieldMenuLinks(tenantSlug, permissions, productsEnabled)` — filtered by permission the same way nav items are, so the menu never offers a screen that answers "you need access" (help carries none: the answers matter most when the API is what failed) — and are deliberately **not** nav items: a nav item's permissions widen its whole zone (availability ORs across the zone's items), so listing Locations/Products on `locations.read`/`products.read` would hand the field zone to every admin and manager holding them. They instead use the `field-menu` `MenuOnlyArea` — an area with no nav label that still resolves to a zone via `zoneForArea`, so the deep-link guard can place those pages. Because the menu hangs off *every* field screen, its links carry the current screen as a `?from=` origin (`withBackOrigin`) and every one of those screens resolves it with `resolveBackTarget`, falling back to the home route on a deep link — otherwise help opened from tasks would return to the route. The locations/products lists carry that origin through their filter forms as a hidden field, since `FilterForm` rebuilds the URL from the form's own fields; the routes screen threads it through its own `routesHref` instead, so opening a route, renaming it or adding a stop (each a server-action redirect) doesn't quietly repoint the back control at the home screen. Planning's "no templates yet" hand-off states the calendar — on the month and day being viewed — as the origin the same way. All of them share one compact header (`.page-header--compact`): the `BackLink` sits `inline` on the title's own row and nothing else is in it, since each is a list and the eyebrow/description stack used to push it a third of the way down the phone. The signed-out and no-permission branches keep the full stacked header — they carry an explanation and no back control. Signing out posts to `/auth/logout` through `lib/session-actions.ts`, which clears the session and CSRF cookies itself rather than trusting the response to have done it (a network error must not leave a working cookie behind).

Persisting a zone choice (`User.lastSelectedZone`, see [data-model.md](data-model.md)) goes through the shared server action `apps/web/lib/zone-actions.ts` (`selectZoneAction`), used identically by the `/choose-zone` chooser and the `AppShell` switcher, which calls `POST /auth/zone` (see [api-reference.md](api-reference.md)) and redirects regardless of whether the persist succeeded — a rejected zone just means the landing page's own `AppShell` guard re-resolves and corrects.

**Known cross-zone overlap**: because zone availability reuses each nav item's existing `requiredPermissions` verbatim (as required — zones must never be derived from role names), a plain `team_manager` has both `field` and `manager` available, not just `manager`: `routes.read` (shared with `field_representative`) makes `field-planning` visible, and `visits.read_team` makes the field overview visible. That overlap is intentional — those are real field-zone permissions a manager holds — so a single-role `team_manager` sees the zone chooser on first login.

The corollary is that a permission shared across roles must never be the *only* gate on a zone's item, or the whole zone leaks. Two items are deliberately gated more narrowly than the endpoint they open for exactly this reason: `admin-pilot` on `tenant.settings.read` rather than `pilot_review.read` (also held by `team_manager` — it previously handed plain managers the entire admin zone), and `manager-potential` on `dashboard.manager.read` rather than `location_insights.read` (also held by field reps and admins). Neither costs a role the screen was meant for — the intended audience holds the narrower permission too. (For `admin-pilot` a `team_manager` does lose access, deliberately: the section is admin configuration work. `manager-potential` loses nobody, since every `team_manager` holds both permissions.) `tests/nav-zones.test.ts` and `tests/zone-permission-mirror.test.ts` pin that a `team_manager`-only permission set yields `field` + `manager` and never `admin`.

### Shared frontend libs (`apps/web/lib/`)

- `api-client.ts` — the only path to the backend. Server-side fetch helpers (`apiGet/apiPost/apiPatch/apiDelete`) that forward the incoming cookie header, `x-request-id`, and the CSRF token, sent as `x-csrf-token`. `buildRequestHeaders(path)` picks `vizitum_platform_csrf` for `/platform/*` paths and `vizitum_csrf` otherwise, matching the backend's per-domain CSRF cookie (see `src/modules/auth/csrf.ts`) — a request built for the wrong domain sends a token that won't match either cookie. Returns `ApiResult<T> = { ok: true; data } | { ok: false; status; message }` — screens branch on `ok`, they do not throw. Also holds the frontend response types. Base URL: `API_BASE_URL` env (default `http://127.0.0.1:4000/api`).
- `navigation.ts` — `buildTenantNav(tenantSlug, permissions)` returns nav items filtered by required permissions (a nav item shows if the user has _any_ of its `requiredPermissions`) and tagged with a `zone`. Add new screens here with their permission requirements and zone. Also exports the zone helpers described above: `availableZones`, `resolveDefaultZone`, `zoneHomePath`, `resolveZoneLanding` — all pure (no fetch calls), unit-tested directly from `tests/nav-zones.test.ts`.
- `back-navigation.ts` — where a `BackLink` points. A screen with several entry points can't hardcode one destination, so the linking screen appends its own tenant-relative location as `?from=` (`backOrigin(path, filters)` + `withBackOrigin(href, origin)`) and the target resolves it (`resolveBackTarget(tenantSlug, from, fallback)`), falling back to the hierarchical parent for deep links. `from` is matched against the `RETURNABLE_SCREENS` allowlist, which both rejects an off-site/cross-tenant/unlisted value and supplies the `common.back.*` label — so the control always announces the screen it really lands on; it must additionally share a zone with the `fallback` (read off the fallback href), since the allowlist is global and no real journey crosses zones. Origins nest (locations list → card → visit history → report), bounded by a 2048-character cap sized for a full-length Cyrillic `search` filter carried three levels deep — each level re-encodes the one below it, so that case runs to ~1500 characters. Pure and framework-free, unit-tested from `tests/web-back-navigation.test.ts`.
- `field-db.ts` — the one IndexedDB connection (`vizitum-field`) the field zone's five on-device stores share, plus the helpers that make raw IndexedDB bearable. Hand-rolled rather than a wrapper: the surface is get/put/delete/cursor and every caller has to degrade instead of throwing, since private browsing, a quota refusal and an old WebView all fail here and none of them may take a report screen down. The five stores are separate because their lifetimes genuinely differ, and conflating them would mean deleting the wrong thing at sign-out — `report-drafts` (retypeable: cleared on sign-out, swept by age), `pending-media` (not recreatable: kept across sign-out, swept by age), `report-outbox` (work already signed off: kept across sign-out and never swept, because a report nobody sent is not stale, it is missing), `visit-start-outbox` (a visit started with no signal: never swept, never even deleted on success — see that store's own entry below for why), `route-snapshot` (today's route, refreshed on every render, not scoped by user like the other four — see `route-snapshot.ts` below). Stores are created per name in `onupgradeneeded` rather than switched on the old version, so a device arriving from any earlier version ends up with all of them. `commitTransaction` resolves on the commit rather than the `put` request, because a quota refusal aborts the transaction *after* the request succeeds and that difference decides whether "saved on this device" is true. `runOnFieldDatabase` is what every operation in the three store modules runs through: it owns the handle, the caller's fallback, and a deadline (5 s, or 1 s for the deletes a user is waiting behind). IndexedDB does not only fail, it can also never answer — and three flows wait on a result before the rep may move on: sign-out, the redirect after a confirm, and the outbox enqueue on every save. A stall in any of them is a button that does nothing; it also used to disable drafts for a whole visit, since nothing may be written until the restore has finished reading. Timing out abandons the wait, not the work.
- `offline-drafts.ts` — the two of those stores the report form itself reads and writes. `report-drafts` is keyed by tenant + user + visit (reps share phones, so a half-typed report must never surface under the next login) and swept after 14 days. `pending-media` holds recorded or photographed bytes that have not reached storage yet and is deliberately **not** cleared on sign-out: a typed report can be retyped, a conversation that already happened cannot be recorded again. Those bytes stay keyed to the rep who captured them so the next person to sign in cannot reach them, and they age out after 7 days, because iOS Safari evicts script-writable storage after seven without a Home Screen install and a longer retention is a promise the platform does not keep. IndexedDB is not encrypted at rest; that residual risk is accepted deliberately, on the grounds that losing the recording is the worse outcome for the person doing the work. Bytes are stored as `ArrayBuffer` with the mime type beside them, not as the `Blob` the recorder hands over — WebKit can drop the file behind a stored Blob while the record survives, which surfaces only at retry as a zero-length upload the server accepts without complaint. The bytes and the storage registration they consumed are two records, so recording the id costs one small write instead of rewriting megabytes; writing fresh bytes clears that registration in the same transaction, since otherwise a replacement capture would be paired with the previous one's storage object and uploaded into it. `hasPendingMediaBytes` is a `getKey()`-only existence check for callers — the pre-cancel notices in `cancel-visit-modal.tsx` and `abandon-visit-start.ts` — that need to know whether bytes are pending without materializing a multi-megabyte `ArrayBuffer` to find out. A draft key can also hold a **forwarding address** instead of a report, which is how the store copes with the one writer it cannot reach: when a visit started offline resolves under the server's own id, `rekeyDraft` moves the draft onto that id, but the report form is still mounted on the old one, with a debounced write already scheduled and one more guaranteed at unmount, and nothing can tell it from outside that the id under its feet just changed. So `rekeyDraft` leaves a record saying where writes go now — written whether or not there was a draft to move, since the rep may not have typed yet — and `readDraft`/`writeDraft`/`deleteDraft` all follow it (one hop only: a client id forwards to a server id, and a server id is never rekeyed again). `discardDraft` is the same mechanism pointing nowhere, for `abandon-visit-start.ts`: the draft goes and a late write is dropped rather than resurrecting one under an id nothing will ever navigate to again. Before this, both of those writes landed back under the dead id as an inert duplicate only the 14-day sweep cleared. Pinned by `tests/web-offline-drafts.test.ts`, the first test here to run against a real (`fake-indexeddb`) database rather than a pure slice.
- `report-outbox.ts` — the third of `field-db.ts`'s stores: confirms the rep has already signed off but the server has not seen, one per visit (`outboxKey` is tenant + user + visit, so a re-confirm before the first send goes out replaces rather than duplicates). Enqueued by the report form on every confirm attempt, before the network call goes out; `report-outbox-flush.ts` drains it sequentially, oldest first, and `report-outbox-indicator.tsx` renders the "N waiting" / "N need attention" chip mounted in the field layout. `hasReportOutboxEntryForVisit`/`deleteReportOutboxEntryForVisit` exist for `cancel-visit-modal.tsx` (and, for a visit that never synced at all, `abandon-visit-start.ts`): cancelling locks the visit, so a queued confirm left behind would hit the server's own `VISIT_NOT_ACTIVE` guard on its next flush attempt and land in "needs attention" for good — the recovery text that state shows ("open the visit and save it again") stops being reachable the moment the cancel that stranded it succeeds. Both are `getKey()`-based, like `hasPendingMediaBytes` above, since the caller only needs to know whether an entry exists and, if so, remove it — never its payload. `rejectReportOutboxEntryForVisit` is the third of that family and the one that is not a delete: `visit-start-outbox-flush.ts` calls it when the server *rejects* the deferred start a queued confirm belongs to. The visit that confirm names can then never exist, so every flush sends it, is answered `VISIT_NOT_FOUND`, and correctly re-queues it as "the start hasn't caught up yet" — a pending count that can never reach zero, with nothing said about why. Marking it moves it into "needs attention" instead, and it happens *before* the start's own rejection is recorded — two separate transactions, and a tab dying between them with the start already marked would strand the transfer for good, since a rejected start is skipped by every later automatic flush. It is not deleted, because it is work the rep already signed off, and the manual "send now" still retries it — which is not futile, since that same tap retries the rejected start first and `rekeyReportOutboxEntry` clears the mark when the start succeeds. Pinned by `tests/web-report-outbox.test.ts`.
- `visit-start-outbox.ts` — the fourth store, for visits started with no signal at all: a device-minted `clientVisitId` and enough to recreate the `POST /visits` call, one entry per attempted start rather than one per visit (no natural "replace" target the way a confirm has — each tap mints a fresh id). Never deleted on success, unlike every other store here — `resolvedVisitId`/`resolvedAt` mark it done instead, because the record is the only mapping from the client id to whatever the server actually did with it, and one of the four backend outcomes (the rep's own already-open visit on the same route stop gets adopted — see `VisitsService.resolveRouteItemLink` in `api-reference.md`) creates no row of its own to carry that id at all — the server records it in `VisitClientAlias` instead, which is what keeps `GET /visits/<clientVisitId>` working for every device that adopted the same visit rather than only the first. `visit-start-outbox-flush.ts`'s `flushVisitStartOutbox` drains it the same way `report-outbox-flush.ts` does, reusing its `classifyReportSendResult`/`outcomeForThrownSend` unchanged, but only marks an entry resolved once `rekeyPendingMedia` (`offline-drafts.ts`) and `rekeyReportOutboxEntry` (`report-outbox.ts`) — moving the pending media and any already-queued confirm from the client id to the real one, patching the confirm's `visitId` field and not just its key — have actually landed (the draft rekey is best-effort, convenience state). If either load-bearing rekey fails, the entry is left alone, but the next cycle does **not** replay `POST /visits` — it retries only the rekey. `remoteVisitId`, a separate field recorded durably the moment the create first answers (before any rekey is attempted), is what stops this device re-sending a create whose answer it *did* hear but whose own rekey hasn't landed — the case that field was added for. The other half, this device never hearing the answer at all (a lost response, not a slow rekey), is closed server-side and not here: `VisitsService`'s adopt branch records the adopting client id in `VisitClientAlias`, so a plain retry finds the visit through the ordinary replay lookup regardless of how many cycles it takes, whether the adopted visit has since closed, or whether another device adopted the same visit first — a single column took only the first adopter's id, and the second one's retry, finding nothing to replay onto and a closed slot, used to mint a second unwanted visit for a stop already done. `decideVisitStartFlushAction`, pure and pinned by `tests/web-visit-start-outbox-flush.test.ts`, is what `flushVisitStartOutbox` asks on every entry to tell send from rekey-only from skip. `visit-start-actions.ts` is the `"use server"` wrapper `createVisitAction` goes through, since `api-client.ts` is server-only by construction (`cookies()`/`headers()`) and there is no other path from a client component to the backend at all. Flushed by `report-outbox-indicator.tsx` ahead of confirms, so a queued confirm for a visit whose start has not synced yet never reaches the server before it has to (see `report-send-outcome.ts`'s `VISIT_NOT_FOUND` handling for the one case it still can, and `pending-visit-report.tsx` in the route table above for the screen this whole store exists to keep working).
- `route-snapshot.ts` — the fifth store, today's route rather than anything the rep typed or started: `writeRouteSnapshot`/`readRouteSnapshot`, a plain overwrite-the-one-row get/put pair over the store `field-db.ts` defines, refreshed on every render of `field/page.tsx` for a real, signed-in, non-demo session (via `route-snapshot-writer.tsx` above). Keyed by tenant slug alone, unlike the other four stores here — the deliberate exception, not an oversight: `apps/web/public/offline.html`, the one other reader, is a standalone script the service worker serves in place of a failed navigation and has no session of its own to learn a user id from. That is exactly why the `pending-media` comparison doesn't hold, despite the surface similarity: `pending-media` survives sign-out safely *because* it is keyed to the rep who captured it, so the next person to sign in on a shared phone cannot reach it — this store has no such protection, so leaving it behind would make it reachable by anyone who opens this tenant's field zone offline next, not just the next person signing in as this same rep. `deleteRouteSnapshot` is what closes that: called from `field-menu.tsx`'s sign-out handler alongside `clearDrafts()`, on the same footing as a draft rather than as a recording. No sweep by age either: a stale snapshot with a visible timestamp is still strictly more useful than none, unlike a draft or a recording, which actually goes stale in a way that matters. The stored `labels` (heading, offline banner, visited/not-visited badges) are pre-resolved, tenant-language text, not raw ICU keys — `offline.html` sits outside the Next.js module graph entirely and has no `next-intl` of its own to draw on, so whatever it shows has to already be in the right language by the time it lands here; the one hardcoded English string left (a "no snapshot exists yet for this tenant" message, shown when nothing has ever been written) is a narrow, deliberate exception of the same shape as `platform/*`'s English-only rendering. Does **not** feed `pending-visit-report.tsx`'s shelf-check matrix, despite being the obvious source: that would need each stop's full assortment, there is no batched "assortment for N locations" endpoint, and fetching it per stop would add ~15 new backend calls to *every* field-home render, online or not, for a fallback case that is otherwise already a graceful (not broken) empty state — deliberately left as a known gap rather than solved at that cost.
- `abandon-visit-start.ts` — the way back out of a start nobody wants: a visit the rep began with no signal, never synced, and has now decided against. Not a variant of `cancel-visit-modal.tsx` and not merely a smaller one — there is no visit on the server to cancel, so nothing is sent, no reason is collected (nobody would ever read one about a visit that existed only on this phone), and the whole operation is a delete of the queue entry plus the draft, both pending-media kinds and any queued confirm keyed to that `clientVisitId`. The draft is *discarded* rather than deleted (`discardDraft`, see `offline-drafts.ts` above): abandoning happens from the report screen as often as from the location card, and that screen's own unmount write cannot be cancelled from out here, so a plain delete loses that race whenever the rep typed something before deciding against the visit. The queue entry goes first and alone, because it is the only one of them that can still become a visit on the server; the rest are bytes two sweeps would reclaim anyway, so a device that stops answering halfway through has already done the half that mattered. The reason this is a module rather than a handler in the component: the background flush (`report-outbox-indicator.tsx`, and `pending-visit-report.tsx`'s own 15s poll) can resolve the very start being abandoned between the render that offered the control and the tap that takes it — so `decideAbandonVisitStart` re-reads the entry rather than trusting the render, and a start that synced in the meantime sends the rep to the real visit instead of deleting a real visit's work (pure, and pinned by `tests/web-abandon-visit-start.test.ts`) — a real visit is anything with either `resolvedVisitId` (every rekey has landed) or `remoteVisitId` (the server has answered, the rekey specifically hasn't) set, since either one means deleting the entry would strand a visit rather than abandon a local-only one. The narrower window — a create already in flight when the delete lands — needs no tombstone to close: `visit-start-outbox-flush.ts`'s `resolveVisitStart` only ever patches an existing record, so it finds nothing to write back, and the visit the server did create reappears on the location card as an ordinary "Continue visit", cancellable the normal way.
- `field-report-draft.ts` — the shape of an unconfirmed field report as it sits on the device, split out of the form so the storage plumbing stays generic and the part that can be got wrong silently is testable without a browser. `isEmptyFieldReportDraft` decides what counts as work worth keeping (opening a panel does not; a visit date only once it moves off the day the form was opened), `parseFieldReportDraft` guarantees a draft read back can never break the form (unrecognized values degrade to defaults, values the form could not display are dropped), and `resolveDraftVisitDate` clamps a restored date into the backdate window a 14-day-old draft can outlive. Pure, unit-tested from `tests/web-field-report-draft.test.ts`.
- `use-field-report-persistence.ts` — the two hooks the report form drives that storage through: `useFieldReportDraft` (restore once, and only over a form the rep has not touched; debounced writes; an immediate write on `visibilitychange`/`pagehide`, since a backgrounded phone does not wait out a debounce; `close()` once the report is on the server) and `usePendingCaptures` (bytes and their registration read back together). Split out because the form had passed 1,800 lines holding two unrelated jobs, and these rules are only correct in a particular order — nothing may be written before the restore has read, and nothing may be written after the report is confirmed, or the flush on unmount writes the draft back over its own delete.
- `storage-retry.ts` — `isStorageObjectGone`, the rule deciding whether a capture held on a phone may still re-sign the storage object it already registered. Only a verdict about the object counts (the `STORAGE_OBJECT_*` codes, plus a bare 404); no answer at all must not, because in a dead zone that is the ordinary outcome and re-registering leaves a duplicate storage object — and, for audio, a duplicate `VisitNote` — behind on the visit. Pure, unit-tested from `tests/web-storage-retry.test.ts`.
- `zone-actions.ts` — `selectZoneAction`, the shared `"use server"` action that persists a zone pick (`POST /auth/zone`) and redirects; used by both the chooser and the `AppShell` switcher. The form-supplied tenant slug is shape-checked (`isTenantSlug` from `tenant-locale.ts`) before being interpolated into the redirect path, so a crafted value can't turn the redirect cross-origin.
- `backend-cookies.ts` — cookie forwarding helpers for server components.
- `error-reporting.ts` — SDK-free Sentry reporter for the web app, mirroring `src/common/sentry.service.ts`'s envelope approach (the workspaces share no code, so this is a deliberate self-contained copy). Configured by `NEXT_PUBLIC_SENTRY_DSN`/`_ENVIRONMENT`/`_RELEASE` (silent no-op when unset), fail-safe on every path, with per-pageload dedupe and an event cap so an error loop can't flood Sentry. Three capture surfaces feed it: `components/error-monitor.tsx` (mounted once in the root layout; `window.onerror` + `onunhandledrejection`), `app/global-error.tsx` (root render errors; copy pinned to the `uk` dictionary since it renders outside the locale provider), and `instrumentation.ts`'s `onRequestError` (Next server-side render/action/route errors, tagged `module: web-server`). Events carry no cookies, headers, form values or PII. Pure core unit-tested from `tests/web-error-reporting.test.ts`.
- `demo-mode.ts` — demo data fallback, controlled by `ENABLE_DEMO_FALLBACK` / `NEXT_PUBLIC_ENABLE_DEMO_FALLBACK`; disabled by default in production.
- `tenant-locale.ts` — supported locales (`en`, `uk`), tenant-slug extraction from the pathname and the locale/timezone lookup against `GET /tenants/:slug/locale` (fail-open to `en`/UTC).
- `branding.ts` — the four tenant color presets as CSS-variable maps (`--accent*`, `--sidebar-*`; scheme ids mirrored against `src/modules/settings/branding.ts` by `tests/branding-scheme-mirror.test.ts`), `buildSchemeStyle` (emits the `:root` override block; the default `emerald` emits nothing) and the picker swatches.
- `tenant-branding.ts` — `resolveTenantBranding(slug)`: branding lookup against `GET /tenants/:slug/branding`, fail-open to emerald/no-logo, wrapped in React `cache()` so the tenant layout, `AppShell` and login page share one fetch per request. Rendered into the page by `app/[tenantSlug]/layout.tsx` — a deliberate, chrome-free exception to the "no per-zone layouts" convention that only injects the `:root` CSS-variable override (and by `BrandMark` in `components/brand-mark.tsx`, which shows the uploaded logo or the default "V" glyph).
- `format.ts` — locale-aware date/enum formatting helpers: `formatDateTime`/`formatShortDate` take a next-intl formatter (honors the tenant timezone), `formatEnumLabel` translates enum-like values via `common.labels.*` with a humanized fallback.
