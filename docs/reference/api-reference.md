# API Reference

Reference for the implemented HTTP API. Source of truth: `src/modules/*/**.controller.ts`, `src/modules/*/**.types.ts`, `src/main.ts`, `src/common/api-error.filter.ts`. Update this document in the same change as any controller change.

All routes are prefixed with **`/api`** (set in `src/main.ts`). Paths below omit the prefix.

## Authentication model

- **Session cookie (tenant)**: `vizitum_session` (httpOnly, SameSite=Lax, Secure in production). Two deadlines, both enforced: a 7-day absolute TTL and a 72-hour idle timeout measured from `sessions.lastSeenAt` (`SESSION_TTL_DAYS` / `SESSION_IDLE_TIMEOUT_HOURS` in `auth.constants.ts`). Set by `POST /auth/login` and `POST /auth/invites/accept`; cleared by `POST /auth/logout`; **rotated in place** by `POST /auth/role` and `POST /auth/zone`, which re-issue both this cookie and the CSRF one. The server stores only a hash of the token (`sessions.sessionTokenHash`).
- **Session cookie (platform)**: `vizitum_platform_session` (same cookie attributes, much shorter life: 12-hour absolute TTL, 2-hour idle timeout — one account reaches every tenant's data). Set by `POST /platform/auth/mfa` or `POST /platform/auth/mfa/enroll`, never by the password step alone; cleared by `POST /platform/auth/logout`. Resolves to a `PlatformUser` and grants the full `platform_owner` permission set (`platform.tenants.read`/`manage`, `platform.operations.read`). Not bound to any tenant; `RequestContext.tenantId` is the sentinel `"platform"` and `userId` is the platform user id (used as the audit actor).
- **CSRF**: double-submit cookie, namespaced per auth domain so one domain's login can't invalidate the other's session — `vizitum_csrf` (tenant, readable by JS) and `vizitum_platform_csrf` (platform, readable by JS) must be echoed in the `x-csrf-token` header on every non-GET/HEAD/OPTIONS request that carries the matching session cookie. The token is an HMAC signed with the session token; `/platform/*` routes validate `x-csrf-token` against `vizitum_platform_csrf` + `vizitum_platform_session` only, tenant routes validate against `vizitum_csrf` + `vizitum_session` only — there is no cross-domain fallback, so a request on one domain's routes with only the other domain's session skips CSRF entirely and is rejected downstream by `PermissionGuard` instead. Errors: `CSRF_TOKEN_REQUIRED`, `CSRF_TOKEN_INVALID`, `CSRF_TOKEN_MALFORMED` (403/400). `POST /auth/logout` and `POST /platform/auth/logout` are exempt from this check (see `src/modules/auth/csrf.ts`): a forged cross-site logout can only ever end the caller's own session, so the accepted "logout CSRF" trade-off is preferred over letting a stale/missing CSRF cookie block session revocation while the session cookie is still valid.
- **Tenant resolution**: the tenant session is bound to a tenant at login (`tenantSlug` in the login body). `PermissionGuard` (`src/modules/auth/permission.guard.ts`) loads the session, tenant, user and roles, and attaches a `RequestContext` to the request. Tenant id is **never** read from client input on tenant-owned routes.
- **Platform bearer token**: `Authorization: Bearer <token>` grants only `platform.operations.read` — a service credential used by `GET /operations/summary` (e.g. the alerts check) and by the proxy diagnostic on `GET /health/readiness`. It **cannot** manage tenants; tenant management requires a `platform_owner` session. Validated against `PLATFORM_OPERATIONS_TOKEN_SHA256` (preferred) or `PLATFORM_OPERATIONS_TOKEN`. Readiness is the one place the token is read outside `PermissionGuard` (`auth/platform-operations-token.ts`): that route has to stay unauthenticated for uptime monitors, so it withholds one block of its answer instead of refusing the request — a caller whose token is wrong, or a deployment with no token configured at all, gets the same response an anonymous caller does, with no error to tell the two apart.
- **Permissions**: endpoints declare `@RequirePermissions` (all required) or `@RequireAnyPermissions` (at least one). Missing permission → 403 `MISSING_PERMISSION`; missing/invalid session → 401 `AUTHENTICATION_REQUIRED`. See [permissions.md](permissions.md).
- **Request id**: `x-request-id` is accepted/generated and echoed in error bodies and some responses.

## Error envelope

All errors are JSON (`src/common/api-error.filter.ts`):

```json
{
  "code": "IMPORT_TEMPLATE_INVALID",
  "message": "Import template type is required.",
  "details": {},
  "fieldErrors": { "templateType": ["Import template type is required."] },
  "requestId": "..."
}
```

`details` and `fieldErrors` are optional. Unhandled errors → 500 `INTERNAL_SERVER_ERROR`. 5xx errors are reported to Sentry.

Paginated list responses share one shape: `{ items, page, pageSize, total, totalPages }`.

## Endpoints

Legend: **all** = `@RequirePermissions` (every permission required); **any** = `@RequireAnyPermissions` (one is enough). Public = no guard.

### Routes on the class-validator DTO track

Item 2.4 in `docs/security-remediation-plan.md` deferred a global `ValidationPipe` and migrated modules one at a time instead. **That migration is now complete: every write route taking a `@Body()` has a DTO in front of it.** There is still **no global pipe** — each route carries its own `@UsePipes(createStrictValidationPipe())` (`src/common/strict-validation-pipe.ts` — `whitelist: true, forbidNonWhitelisted: true, transform: true`) — and that stays deliberate rather than pending: a route-scoped pipe is visible at the handler a reader is already looking at, and a new controller written without one fails its own tier's `PIPES_METADATA` test rather than silently inheriting a whitelist nobody declared a DTO for. What a gated route does differently, uniformly: a property the DTO does not declare is refused with 400 `VALIDATION_FAILED` and a `fieldErrors` entry naming it, before the handler runs. A failure inside a nested object is keyed by its path (`products.0.id`) — class-validator hangs nested errors off the parent's `children` with no constraints of its own, so the pipe walks them rather than answering with an empty `fieldErrors`. Beyond that the DTO is a **coarser gate in front of the service, not a replacement** — the module's own `normalize*`/`parse*` helpers still run unchanged afterward and remain the source of truth for required-ness, trimming, uniqueness and calendar validity, so their existing error codes (`CHAIN_INVALID`, `TASK_INVALID`, `ANNOUNCEMENT_INVALID`, …) are unchanged. Each section below notes what its own DTO adds; the sections for ungated routes describe the service's validation alone.

Two shapes of change are shared by the flat-CRUD group (chains, both category vocabularies, products, announcements, tasks, locations) and worth stating once. **Caps moved earlier:** where a normalizer folded an over-length value into the same answer as a missing one, the DTO now reports it as over-length. **Silently-ignored values became refusals:** an enum-ish field outside the set the service recognises used to be mapped to null and dropped (or, for `PATCH /tasks`, to `in_progress` — a typo'd status reopened a finished task), all under a 200; those are now 400 `VALIDATION_FAILED`. Non-boolean values for `isPriority`/`notApplicable` are the same story.

`locations` adds a third shape to that list, from the same root: **a non-string where a string was expected used to mean "clear this field".** `normalizeId` and `normalizeOptionalString` answer `null` for a value of the wrong type, and on a PATCH the field is *present*, so that null was written rather than ignored — `{"chainId": 0}` unlinked the location's chain, and `{"email": 42}` erased a contact's email, both under a 200. `@IsString()` is what refuses those. A deliberate `null` still clears, on every field that documents it.

### Auth — `/auth` (public, `auth.controller.ts`)

| Method & path               | Body                                             | Returns                                                                                                            |
| --------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `POST /auth/login`          | `{ email, password, tenantSlug, captchaToken? }` | `{ user: { id, email, firstName, lastName, name, status, lastSelectedRoleCode, lastSelectedZone }, roleCodes, permissions }` (`name` is the composed display value, `lastName` null only on legacy rows); sets session + CSRF cookies. When `TURNSTILE_SECRET_KEY` is set, `captchaToken` (Cloudflare Turnstile) is required and verified server-side — 400 `CAPTCHA_INVALID` on a missing/rejected token (see [environment.md](environment.md)). Rate limited: 30 requests/minute per client address (429 `RATE_LIMITED` with `Retry-After`), and each failed attempt against a given tenant+email earns a growing delay — capped, and never a refusal, so nobody can lock an account out by guessing at it. Refusals of the *workspace* land before the password is looked at at all, from `TenancyService.assertTenantCanServeRequests`: 403 `TENANT_UNAVAILABLE` for a `suspended`/`archived` tenant, 403 `TENANT_NOT_READY` for any status outside the serving set `pilot`/`team`/`business` (in practice a retired `draft`/`provisioning`/`ready`/`active` row — see [data-model.md](data-model.md)), both with `details.status`; an unresolvable slug is 404 `TENANT_NOT_FOUND`. The web login screen renders those two 403s as their own message instead of the credential one (`apps/web/lib/login-error.ts`, pinned by `tests/web-login-error.test.ts`) — folded together, a workspace that was switched off read back as a wrong password, which cost a real debugging session on a staging tenant left on `ready` after the status/plan migration. Credential failures stay 401 `INVALID_CREDENTIALS` and stay single-valued: "no such user" and "wrong password" are deliberately the same answer, so neither the API nor the screen may reintroduce the difference. Every outcome is audited (`auth.login_succeeded`/`auth.login_failed`, see [data-model.md](data-model.md)) — including an attempt against an address that matches no account, which is the case the trail most needs. Both failure paths write, so the audit adds the same cost whether or not the address exists and does not reintroduce the timing difference the response avoids |
| `GET /auth/me`              | —                                                | Same shape as login, plus `productsEnabled` (tenant setting, used to hide the Products nav item), `locationCategoriesEnabled` (tenant setting, defaults to enabled when unset), `tenantTimezone` (IANA zone from `PlatformTenant.timezone`, used to render dates in the tenant's local time), `tenantSlug` (`PlatformTenant.slug`, `null` only if the session outlived its tenant row) and `pilotActive` (`true` while `PlatformTenant.status === "pilot"`, used to show/hide the temporary "Pilot" admin nav area). `tenantSlug` is which workspace the session *belongs to*, which no other part of a request states: the session token carries the tenant and no header names one, so a session for `acme` reading a screen under `/other-co/...` is answered with acme's data. Anything that acts on a session rather than just rendering it has to compare the two first — the login screen's already-signed-in redirect does (`apps/web/lib/login-redirect.ts`, pinned by `tests/web-login-signed-in-redirect.test.ts`) |
| `POST /auth/role`           | `{ roleCode }`                                   | Switch `lastSelectedRoleCode`. Rotates the session token and re-issues the session + CSRF cookies: the switch changes what the session may do, so the token it was carrying stops working                    |
| `POST /auth/zone`           | `{ zone }`                                       | Switch `lastSelectedZone` — `zone` must be one of `field`/`manager`/`admin`/`operations` (400 `INVALID_ZONE`) and must be available to the caller's current permissions per `src/modules/auth/zones.ts` (400 `ZONE_NOT_AVAILABLE`; mirrors the zone tags in `apps/web/lib/navigation.ts`, see [module-map.md](module-map.md)); not a new authorization check — every controller still enforces its own permissions, this only validates a stored UI preference. Same response shape as `POST /auth/role`, and rotates the session token the same way. Not audited (same as `POST /auth/role`) |
| `POST /auth/invites/accept` | `{ token, tenantSlug?, firstName, lastName, password, phone? }` | Activates invited user, sets session + CSRF cookies; a token that doesn't resolve to a pending, unexpired invite for the matching tenant is 400 `INVITE_INVALID`; `firstName` and `lastName` are both required (400 `INVITE_ACCEPTANCE_INVALID` with per-field errors) and the stored display `name` is composed from them; `phone` is parsed against the invite tenant's `phoneCountry` (`+`-prefixed input is accepted as any-country international) and stored as E.164 — an unparseable phone is a 400 `INVITE_ACCEPTANCE_INVALID` with a `phone` field error. The web accept screen deliberately no longer collects a phone (the number was never surfaced anywhere in the product, so the field was pure signup friction); `phone` stays accepted here for API clients and imports, and a user's number is set later through `PATCH /users/:userId` or a users import; when `tenantSlug` is supplied it must match the invite tenant; accepting a `company_admin` invite re-checks 409 `TENANT_ADMIN_LIMIT` (closes the gap where several pending admin invites could collectively exceed the limit); an invite is refused with 409 `INVITE_ACCOUNT_ALREADY_ACTIVE` when the address already belongs to a live account (an invite stays valid for its 7-day TTL, and without this a stale one could overwrite the password of an account created in the meantime); accepting a `tenant_superadmin` invite demotes any other currently active superadmin in the tenant to a suspended `company_admin` (audited as `superadmin.replaced`) — a role swap, not just deactivation, so the demoted account stays reachable through the ordinary admin lifecycle instead of being permanently stuck behind `SUPERADMIN_PROTECTED` |
| `POST /auth/logout`         | —                                                | `{ ok: true }`; revokes session, clears cookies. Audited as `auth.logged_out` against the session's own account, resolved before the revocation that makes the session unfindable; cookies are cleared even when no live session matched                                                                    |

All four write routes are on the [class-validator DTO track](#routes-on-the-class-validator-dto-track) — the last tier, and the one where the DTO does **least**. On these bodies it declares which properties may exist and the type of each, and makes no other judgement: no length cap on a password or an invite token, no `@IsIn` on `roleCode` or `zone`. `INVALID_CREDENTIALS` is deliberately one answer to a missing account, an inactive one and a wrong password (item 3.1 went as far as equalizing the *timing* of the three), so a DTO refusing an over-long password with its own message would add a second kind of answer to the screen that has spent the most effort having only one; `INVALID_ROLE` and `INVALID_ZONE` are loud refusals the service already makes, and `auth.service.ts` keeps its own role list because "roles a user may operate as" and "roles an admin may grant" are different questions with the same answer today. The one exception is `firstName`/`lastName` on the invite acceptance — ordinary profile text, capped at the same `TEXT_LIMITS.name` `normalizeNamePart` already enforced by discarding the value, so a 200-character name no longer comes back "First name is required."

Two facts about ordering, since this is where they matter most and both were measured rather than assumed. **A body the DTO refuses is not a free attempt**: Nest runs guards before pipes, so the per-IP throttle has already charged for it — ten malformed platform logins in a row answer `400, 400, …` and then `429`. And **a body the DTO refuses cannot become an unlogged login attempt**, because `AuthService.login` already refuses the same class of body — a missing, blank or non-string email/password — *before* the captcha check, the per-account backoff and `recordTenantLoginFailed`. A malformed login has never been a recorded attempt; the DTO changes only the status code, and only for a body no client sends. An empty string is not such a body: `{"email": "", "password": ""}` is what a blank login form posts, `@IsString()` accepts it, and it still comes back 401 `INVALID_CREDENTIALS`.

### Password recovery — `/auth/password` (`password.controller.ts`)

All three carry a hard per-IP throttle on top of the finer per-account controls described below (15/min for forgot and reset, 10/min for change); over it the answer is `429 RATE_LIMITED` with `Retry-After`.

`forgot` and `reset` are public; `change` reads the session cookie directly (there is no permission for acting on your own account). All three are audited on the target user (`password.reset_requested`, `password.reset_completed`, `password.changed`).

| Method & path                  | Body                                        | Returns                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------ | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /auth/password/forgot`   | `{ email, tenantSlug?, captchaToken? }`     | Always `{ ok: true }` with a 200, whether or not the address matches an account — a tenant's member list is not public, so anything else turns the login screen into a membership oracle. That extends to *timing*: once the address resolves to an active account, issuing the token, sending the mail and writing the audit row all run off the response path, so a known address does not answer measurably later than an unknown one. Only an `active`, non-deleted user is mailed (an `invited` one still holds an invite; a suspended/deleted one must not get a way back in). Rate limited per client IP (`PASSWORD_RESET_IP_LIMIT` per 15 min, in-process — requires `TRUST_PROXY_HOPS`, see [environment.md](environment.md)) and per account (`PASSWORD_RESET_MAX_ACTIVE_TOKENS` live tokens, enforced inside a serializable transaction so concurrent requests can't both pass the check); over either ceiling the request is dropped silently. When `TURNSTILE_SECRET_KEY` is set, `captchaToken` is required — 400 `CAPTCHA_INVALID` is the one failure this endpoint does surface |
| `POST /auth/password/reset`    | `{ token, tenantSlug?, password }`          | `{ ok: true }`. 400 `PASSWORD_RESET_INVALID` for a token that is unknown, already spent, past its `PASSWORD_RESET_TTL_MINUTES` expiry, belonging to another tenant than `tenantSlug`, or whose account is no longer active — and for a `password` shorter than `MIN_PASSWORD_LENGTH`. Spending the token, writing the hash, dropping the account's other outstanding tokens and revoking **every** session are one transaction — revocation in particular must not be a follow-up write, or a failure would leave a changed password with whoever prompted the reset still holding a live session. No session is issued here, so the caller signs in again with the new password |
| `POST /auth/password/change`   | `{ currentPassword, newPassword }`          | `{ ok: true }`; requires a session (401 `AUTHENTICATION_REQUIRED`). 400 `CURRENT_PASSWORD_INVALID` when the current password does not verify — re-checking it is what makes the screen safe to reach from an unattended session, and a wrong value earns the same growing per-identity delay a wrong login does (`LoginBackoffService`, its own `password-change` scope, cleared on success) — and 400 `PASSWORD_CHANGE_INVALID` for a missing/short field. The new hash, the revocation of every session and the dropping of any pending reset token are one transaction; a fresh session for this caller is issued only after it commits (new session + CSRF cookies on the response), so other devices are signed out while the person who made the change keeps their screen — and if that last step fails they are simply signed out too, which is the safe direction |

All three are on the [class-validator DTO track](#routes-on-the-class-validator-dto-track), under the same envelope-and-types-only rule as `/auth` above: no `@MinLength` on either new password, because `PASSWORD_RESET_INVALID` and `PASSWORD_CHANGE_INVALID` interpolate `MIN_PASSWORD_LENGTH` into `fieldErrors.password` and that is the message a person retyping a password needs; no minimum at all on `currentPassword`, which deliberately has none (it predates whatever today's rule is, and the only question asked of it is whether it verifies); and nothing on `forgot` beyond the type, because that endpoint acknowledges *everything* so it cannot be used to ask whether an address has an account here — a cap or a format check would make "too long to be an address" a distinct answer from "nothing was sent". `@IsString()` does not weaken that: it separates a malformed body from a well-formed one, while the property being protected is that two *addresses* stay indistinguishable.

### Health — `/health` (public, `health.controller.ts`)

| Method & path           | Returns                                            |
| ----------------------- | -------------------------------------------------- |
| `GET /health`           | Liveness info + `requestId`                        |
| `GET /health/readiness` | Readiness info; HTTP 503 when `status !== "ready"`. `checks.authHardening` reports the controls that degrade silently rather than erroring — `captchaEnabled`, `rateLimitEnabled`, `rateLimitCountersShared` (Redis vs process memory), `trustProxyHops`, and `proxyResolution`: `clientAddress` (what `trust proxy` actually resolved for *this* request, validated as an IP or reported as `invalid`) and `forwardedHopCount` (entries in `X-Forwarded-For`). Curl it from a machine whose public address you know: if `clientAddress` is not that address, set `TRUST_PROXY_HOPS` to `forwardedHopCount`. **The whole block is operator-only** — returned solely to a caller presenting the platform operations bearer token. `proxyResolution` was gated first: in the very state it diagnoses (hops too low) the resolved address is internal infrastructure, and the two numbers together say how many entries to prepend to forge an address on a directly reachable API. The rest followed for the same reason — `trustProxyHops` is half that recipe, and `captchaEnabled: false` or `rateLimitEnabled: false` tells an anonymous reader exactly when the login routes are unopposed. The block is omitted rather than blanked, so "not for you" is distinguishable from "configured as false", and an absent `authHardening` means the token was not accepted — wrong token and no token configured on the server look identical from outside. The route itself stays unauthenticated so uptime monitors keep working (they read `status` and the HTTP code), and the response carries `Cache-Control: no-store` because it varies per caller |

### Platform auth — `/platform/auth` (public, `platform-auth.controller.ts`)

| Method & path                | Body                  | Returns                                                                                                                                                                          |
| ---------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /platform/auth/login`  | `{ email, password, captchaToken? }` | **First step only — never issues a session.** Answers `{ step: "mfa", challengeToken, expiresAt }` for an owner with a confirmed authenticator, or `{ step: "mfa-enrollment", challengeToken, expiresAt, secret, otpauthUrl }` for one without: "not enrolled" is a state the owner passes through, never one they can keep signing in from. 401 `INVALID_CREDENTIALS`; 400 `CAPTCHA_INVALID` when `TURNSTILE_SECRET_KEY` is set and the Turnstile token is missing/rejected. Rate limited to 10 requests/minute per client address. A refused password step is audited as `platform.login_failed` (`metadata.reason`: `unknown_account`/`inactive_account`/`wrong_password`); a *successful* password step is not, because it is not a sign-in — the session, and the `platform.login_succeeded` row, come from the code step |
| `POST /platform/auth/mfa`    | `{ challengeToken, code }` or `{ challengeToken, recoveryCode }` | Second step. `{ step: "session", platformUser, roleCodes, permissions, recoveryCodesRemaining }`; sets `vizitum_platform_session` + `vizitum_platform_csrf`. A recovery code is single-use and struck from the list as it is spent. The challenge is consumed on the first attempt, so a wrong code means starting from the password again — and is charged the same growing delay a wrong password is. 400 `MFA_CODE_INVALID`, 400 `MFA_CHALLENGE_INVALID` (expired, replayed, or claimed for the wrong step). All carry `metadata.method` (`totp`/`recovery_code`, or `enrollment` for the session issued by `mfa/enroll`) — a spent recovery code is worth telling apart from an authenticator |
| `POST /platform/auth/mfa/enroll` | `{ challengeToken, code }` | Second step for an unenrolled owner. The code proves the authenticator holds the challenge's pending secret; only then is the secret committed to the account. Returns the session plus `recoveryCodes` — ten single-use codes, stored hashed, returned exactly here and never again. Audited like the login code step, since it ends in a session too: `platform.login_succeeded` with `metadata.method: "enrollment"`, `platform.login_failed` with `reason: "wrong_code"` on a rejected code, and `reason: "invalid_challenge"` when the challenge is refused. 400 `MFA_CODE_INVALID`, 400 `MFA_CHALLENGE_INVALID` |
| `GET /platform/auth/me`      | —                     | Same fields as the session response from `/mfa`, minus `step` (`{ platformUser, roleCodes, permissions, recoveryCodesRemaining? }`); 401 `AUTHENTICATION_REQUIRED` when unauthenticated                                                                                                          |

All three write routes are on the [class-validator DTO track](#routes-on-the-class-validator-dto-track), and the two code steps are where it stops validating altogether: `challengeToken`, `code` and `recoveryCode` carry `@Allow()` — whitelisted, unchecked. Read the audit column above and the reason is there. `claimChallengeAudited` takes the token as `unknown` and writes `platform.login_failed` (`reason: "invalid_challenge"`) for *any* claim it cannot honour, malformed included; a rejected code is charged to the shared `platform-login` backoff and audited as `wrong_code`. A pipe runs before the service, so an `@IsString()` on those fields would turn `{"code": 123456}` — the shape a naive scripted guess produces by default — into a 400 that leaves no trace, making the laziest attack the only invisible one. The same reasoning already governs `mfaCode` on the tenant purge. The password step is different and does type-check its two fields: it refuses a missing or non-string email/password *before* the captcha, the backoff and `recordPlatformLoginFailed`, so nothing audited is skipped. The classes still earn their place — a property none of them declares is refused on the requests that mint a platform session.

Also fixed here while gating these routes: the password step **did not cap the password length**, though its tenant twin does and explains why (argon2 hashes whatever it is given, so an unbounded password is an unbounded amount of work per request, answered before any account is known). It now applies the same `TEXT_LIMITS.password` bound. This was the third copy of that helper to drift — the second lost its caps in a duplication recorded in the plan's follow-up section, and this one never had them.

A replay with a token this tenant has already seen returns that first attempt's `Report` **unchanged and does no work**: re-running would stamp a fresh `confirmedAt` (hours late, for a rep who was offline when they actually finished) and delete/recreate the report's tasks, discarding whatever a manager had done with the originals. A token already spent on a **different** visit is 409 `REPORT_REQUEST_ID_REUSED` rather than a silent pass-through, since replaying another visit's report as this one's is worse than any error. Two concurrent flushes of the same token race to the unique index; the loser is served the winner's report. All eleven write routes are on the [class-validator DTO track](#routes-on-the-class-validator-dto-track), gated across two changes (see [the design note](../plans/visits-dto-migration-note.md)).

**`confirmedData` is deliberately opaque** on both routes that take it (`reports/confirm`, `ai/drafts/confirm`): the DTO declares it `@IsObject()` and nothing deeper, so the payload reaches the service exactly as sent — no property stripped, none refused. Two reasons, and the second is the deciding one. One route carries two unrelated shapes chosen by `schemaVersion` (`field-report.v1`, and `manual.v1` whose field list comes from the tenant's own `segmentTemplate`), so no single declaration could be right for both. And `apps/web/lib/report-outbox.ts` stores a queued confirm on the rep's device and replays it when signal returns, never retrying one the server refused — so a whitelist that rejected a property an older build sent would destroy a finished report rather than merely refuse a request. The envelope around it *is* closed: `schemaVersion` (64), `clientRequestId` (128) and `extractionJobId` are declared and anything else is refused, which is where mass assignment could actually have reached. `REPORT_INVALID` / `AI_DRAFT_INVALID` remain the service's answer for a missing payload.

**`products[]` on `field-report-transcriptions` is the one nested body on the whole track**, and the one place this migration changes a contract: an entry missing `id` or `name`, or carrying a property the DTO does not declare, is now refused with a path-qualified field error (`products.0.id`) where `parseProductCatalog` used to drop it and transcribe against a quietly smaller catalog. `sku` and `category` stay optional and nullable.

What the six `VisitsService` bodies add: the caps behind them (`visitType` 64, `clientVisitId` 128, cancellation `comment` 500, `textContent` 2000, `fileName` 1024, audio `checksum` 64), a `status` outside `draft`/`in_progress`/`completed`/`cancelled` refused where it used to be dropped under a 200, and a `representativeUserId` refused on every route but create, where it was silently ignored. Three things are deliberately **not** narrowed, because the service's own refusal says more than a whitelist rejection would: `status: "cancelled"` still reaches `PATCH /visits/:visitId` so it can answer "Use `POST /visits/:visitId/cancel`"; an unrecognised cancellation `reason` still reaches `CANCELLATION_REASON_INVALID`, whose message lists every allowed one; and `sizeBytes` is type-checked only (number **or** numeric string, as item 3.2's signed `Content-Length` requires) with every numeric judgement left to `AUDIO_UPLOAD_SIZE_INVALID`/`PHOTO_UPLOAD_SIZE_INVALID`, which name the limit in MB — the message a rep with an over-long recording actually needs. `contentType` is not narrowed to the supported set either: an unsupported value falls back to the file extension rather than failing.

### Tasks — `/tasks` (`tasks.controller.ts`)

A task starts `in_progress` (the default on create) and the only status transition is to `done` — there is no `open` or `cancelled` anymore. Priority is a plain boolean flag (`isPriority`), not a graded scale. Every response below includes `history: TaskStatusHistoryEntry[]` (`{ id, changedByUserId, changedBy, oldStatus, newStatus, createdAt }`, oldest first) — one row from task creation (`oldStatus: null`) plus one per status change, each written in the same transaction as the write it records (see [data-model.md](data-model.md)'s `TaskStatusHistory`). Tasks that predate this table simply return an empty `history` array.

`POST /tasks` and `PATCH /tasks/:taskId` are on the [class-validator DTO track](#routes-on-the-class-validator-dto-track). The DTO caps `title` at 200 and `description` at 2000, requires `isPriority` to be a real boolean, and refuses a `status` outside `in_progress`/`done` — the sharpest of the tier's tightenings, since `parseUpdateTaskBody` read an unrecognised status as `in_progress`, so a typo reopened a finished task under a 200. `dueDate` still accepts `""` alongside a `YYYY-MM-DD` day, which is how the field app clears a deadline. The four id fields carry no length cap on purpose: every other cap here mirrors one the service already enforces, and there is no cap on an id anywhere — they are looked up against the tenant's own rows immediately after, which is the check that matters. The own-scope `assignedToUserId` rules below are unchanged and stay in the service.

### Announcements — `/announcements` (`announcements.controller.ts`)

The tenant notice board: a manager publishes something that holds for a period, every field representative sees it while it is in force, and acknowledging it leaves a receipt. `state` is **derived** on every read from the inclusive, date-only window against today in the tenant's timezone plus `archivedAt` (`scheduled` / `active` / `finished` / `archived`) — it is never sent on a write and nothing has to run for an announcement to start or expire. `startsAt`/`endsAt` are `YYYY-MM-DD` and both included; an `endsAt` before `startsAt` 400s (`ANNOUNCEMENT_INVALID`). `title` is capped at 200 characters and `body` at 2000, mirroring `INPUT_LIMITS` in the web app. There is no delete: withdrawing sets `archivedAt`, which keeps the read record intact. Both write paths that change a published announcement — editing and withdrawing — are audited, so a live notice can't be reworded without a trail.

`POST /announcements` and `PATCH /announcements/:announcementId` are on the [class-validator DTO track](#routes-on-the-class-validator-dto-track), through one `UpsertAnnouncementDto` marking all four fields optional — create requires all four and patch none, and that difference stays in the service. The DTO enforces the 200/2000 caps (imported from `announcements.types.ts`, the same constants the service reads) and the `YYYY-MM-DD` shape of both window ends; calendar validity and the `startsAt <= endsAt` ordering stay in the service, which is where the current row is available to compare a patch against. `POST /:announcementId/archive` and `/read` have no body and are outside the track.

### Location insights — `/locations/:locationId/potential`, `/locations/:locationId/assortment`, `/location-insights` (`location-potential.controller.ts`, `location-assortment.controller.ts`, `location-insights-summary.controller.ts`)

> Mutation scope: the two sub-resources are written by different roles and no longer share a permission. `PUT`/`DELETE .../assortment[/:productId]` require `location_assortment.manage` — held by `team_manager` (who owns the standard an outlet must carry) and, as a service-level fallback with no screen behind it, `tenant_superadmin`; `assertCanManageAssortment` (`src/modules/location-insights/location-insights-access.ts`) is a plain permission check with no ownership tier (403 `LOCATION_ASSORTMENT_SCOPE_FORBIDDEN`). `PUT`/`DELETE .../potential[/:productCategoryId]` require `location_potential.manage_own` (`field_representative`) or `location_potential.manage` (`tenant_superadmin`'s no-UI repair path, mirroring the assortment one), and for the `.manage_own` tier `assertCanManagePotential` additionally requires an **active `LocationAssignment`** for that location (403 `LOCATION_POTENTIAL_SCOPE_FORBIDDEN` — checked live per request, not cached). A representative therefore reads the assortment but cannot write it, which is what keeps the visit report's shelf-check chips a rule set by the manager. Reads (`location_insights.read`) stay tenant-wide for all four roles, same as `locations.read`. Both list endpoints also compute `canManage: boolean` per request so the frontend can hide write affordances without re-deriving the rule. `PUT` is an idempotent upsert — the same call creates the row if it doesn't exist yet or updates it if it does, avoiding a create-then-409-then-patch dance. The assortment `PUT` writes **only** `shouldBeListed`: the shelf state on that row (`status`, `lastCheckedAt`) belongs to whichever visit last checked it — written as a side effect of confirming a visit report (see `POST /visits/:visitId/reports/confirm` below), never through this endpoint — so a manager re-saving the matrix flag must not reset it. The potential `PUT` still replaces its row wholesale — one owner, no split.

> **`PUT .../potential/:productCategoryId` and `PUT .../assortment/:productId` are the first two modules on the class-validator DTO track** that item 2.4 in `docs/security-remediation-plan.md` deferred. Their bodies are typed as `UpsertLocationPotentialDto` (`location-potential.dto.ts`) and `UpsertLocationAssortmentDto` (`location-assortment.dto.ts`), each gated by its own `createStrictValidationPipe()` call (`src/common/strict-validation-pipe.ts` — `whitelist: true, forbidNonWhitelisted: true, transform: true`), attached with `@UsePipes()` on that one route only, not a global pipe. For potential, a property the DTO doesn't declare, or a `comment` over `MAX_COMMENT_LENGTH` (`location-insights-parsing.ts`, 500 — the same constant `apps/web/lib/input-limits.ts` documents), is refused before the request reaches `LocationPotentialService`, as 400 `VALIDATION_FAILED` with `fieldErrors`; `normalizeOptionalDateOnly`/`normalizeOptionalNonNegativeInteger`/`normalizeOptionalComment` still run afterward, unchanged, and remain the source of truth for calendar validity and the exact int4 ceiling (400 `LOCATION_INSIGHTS_VALUE_INVALID`). For assortment, `shouldBeListed` is the DTO's only field — a shelf-state field like `status`/`lastCheckedAt` sent by an old client is now refused by the pipe (400 `VALIDATION_FAILED`) instead of silently dropped; `parseUpsertAssortmentBody`/`normalizeOptionalBoolean` still run afterward, unchanged, and remain the source of truth for defaulting an omitted field to `true`. In both cases the DTO is a coarser gate in front of the service's own normalization, not a replacement. `GET /location-insights/summary` has no body and stays outside this track.

### Routes — `/routes` (`routes.controller.ts`)

> Mutation scope: mutations require `routes.manage_team` or `routes.manage_own` at the guard level; `RoutesService.assertCanManageRouteForRepresentative` then enforces ownership. With `routes.manage_team` the caller may mutate any plan in the tenant; with only `routes.manage_own` the plan's `representativeUserId` must equal the caller's user id (403 `ROUTE_SCOPE_FORBIDDEN` otherwise). `GET /routes/today` is also scoped: `routes.manage_team` sees all of today's plans, everyone else only their own.
>
> Read scope on the two paginated lists (`GET /routes`, `GET /routes/templates`) follows the same rule through one shared helper, `resolveRouteRepresentativeFilter` (`route-access.ts`), so plan and template lists cannot drift apart: a `routes.manage_team` caller gets the representative they asked for, or **every** representative in the tenant when they name none; everyone else is pinned to their own rows and a `representativeUserId` they may not read is ignored rather than refused. Only an own-scope caller with no resolved user id is refused (403 `AUTHENTICATION_CONTEXT_MISSING`). Until this was fixed, a team-wide caller who named no one was refused instead of served, which broke the manager representative-workload screen — it lists routes with pagination only.

All five write routes with a body are on the [class-validator DTO track](#routes-on-the-class-validator-dto-track). The DTO refuses a plan `status` outside the five and an item `status` outside `planned`/`visited`/`skipped` (both were mapped to null and dropped, so a typo returned 200 having changed nothing); requires `sequence` to be an integer ≥ 1 (a non-integer was dropped the same way on the PATCH, renumbering nothing); caps `skipReason` at 200, the `title` key the service reads; and checks that `planDate` is `YYYY-MM-DD`-**shaped** — calendar validity ("2026-02-31") stays with `parseDateOnly`, which shares `DATE_ONLY_PATTERN` with the DTO rather than restating it. Putting a gate in front of that split is what exposed a defect behind it: `parseDateOnly` only checked `Number.isNaN`, and an out-of-range *day* rolls over rather than producing NaN, so `{ "planDate": "2026-02-31" }` was answered **201 for a plan quietly filed on March 3rd**. It now round-trips the parsed date back to a string, as its two siblings in `location-insights-parsing.ts` and `visits/shelf-check.ts` always did; such a date is now 400 `ROUTE_PLAN_INVALID` (or `ROUTE_TEMPLATE_ASSIGN_INVALID` on assign). `publishedAt`, `plannedStartTime` and `plannedEndTime` stay plain strings, since `parseOptionalDateTime` defines that contract more loosely than an ISO pattern would and `""`/`null` are how a caller clears them. `itemIds` must be a list of strings; whether the list is the plan's exact permutation is still `ROUTE_ITEM_REORDER_INVALID` from the service, which is the only layer that knows the plan's items.

`RoutePlanResponse` also carries `routeTemplateId: string | null` and an embedded `routeTemplate: { id, name } | null` summary — set when the plan was created via `POST /routes/templates/:templateId/assign` or `.../copy-month` below, `null` for a plan created directly via `POST /routes`.

Each `RouteItem`'s (and, below, each `RouteTemplateItem`'s) embedded `location` also carries `chain: { id, name } | null` alongside `id, name, addressLine, city` — the same shape documented under Locations above.

### Imports — `/imports` (`imports.controller.ts`)

Template types: `users`, `locations`, `contacts`, `products`, `initial_visit_task_plan`. The `locations` template has optional `chain` and `category` columns: each value is resolved by name (case-insensitive) against the tenant's `Chain`/`LocationCategory` dictionary and created on first use, so a location import can populate both canonical lists without a separate upload; `createdCounts` on confirm includes `chains` and `locationCategories` counters for rows created this way. The validation preview surfaces a `LOCATION_CATEGORY_WILL_BE_CREATED` warning (non-blocking) once per distinct new category name in the file, so auto-creation is explicit rather than silent. The `category` column replaced the legacy `type` column — uploads with an old `type` header are still accepted as an alias and parsed into `category`, but the downloadable template and samples only ever advertise `category`.

`POST /imports/jobs/validate` is on the [class-validator DTO track](#routes-on-the-class-validator-dto-track) — the only route on this controller with a body, and the one the track deferred longest ([design note](../plans/imports-dto-migration-note.md)). **The gate is narrower than it looks, and that is worth stating plainly rather than leaving a reader to assume the import path is now validated.** What it adds is one thing: an undeclared property is refused by name. `templateType` is gated with `@IsIn` because it is the discriminator that picks both the header allowlist and the row validator, and `IMPORT_TEMPLATE_INVALID` never named the allowed values anyway. `csvText` is `@IsString()` and nothing else — a whitelist walks properties and a string has none, so the choice is only whether to declare the field; its size stays bounded by `JSON_BODY_LIMIT` (a larger body is a 413 from body-parser before the pipe), and a `@MaxLength` would restate that limit while replacing the 413 with a field error. `fileName` carries no cap either, unlike the two upload registrations: `parseFileName` truncates at 255 by design because the column is purely informational, so a cap would invent a refusal rather than surface one. Everything that actually defends an import is behind the pipe and unchanged — `assertApprovedHeader` refusing any column the template does not declare (the real anti-mass-assignment control here), the per-column `TEXT_LIMITS` caps, the formula guard, the per-template row validators, and the fact that this route only ever produces a preview. `IMPORT_TEMPLATE_INVALID`/`IMPORT_FILE_INVALID` stay the controller's own answers for a missing or blank value. `POST /jobs/:importJobId/confirm` takes no body and is deliberately ungated.

**An import applies at most 1 000 rows** (`MAX_IMPORT_ROWS` in `imports.service.ts`). A file past that is refused at validation time — one blocking `IMPORT_ROW_LIMIT_EXCEEDED` issue per row over the cap, so `validRowCount` is the number that would fit and `errorRowCount` the number that has to move to a second file — and `POST /jobs/:importJobId/confirm` refuses an over-cap job stored before the cap existed with the same code as a 400. This is a *stated* ceiling rather than the emergent one it replaces: `csvText` is bounded only by `JSON_BODY_LIMIT`, which for a dense template is several thousand rows, and the apply used to be a per-row loop of 5-7 queries inside a transaction carrying Prisma's 5 000 ms default — so a few-hundred-row locations file returned an opaque 500 that no retry could clear (audit F8). The apply now resolves every reference in grouped lookups and writes with `createMany`, which puts a whole file at 1-7 queries whatever its row count (`tests/import-apply-batching.test.ts`), and the confirm transaction passes `maxWait` 10 000 ms / `timeout` 30 000 ms explicitly. The cap is what keeps each batched INSERT inside Postgres's 65 535 bind parameters per statement.

### Admin users — `/admin/users` (`admin-users.controller.ts`)

`roleCode`/`roleCodes` here only ever accept `company_admin`, `team_manager`, `field_representative` — `tenant_superadmin` is never assignable through this controller (400 `INVITE_INVALID`/`INVALID_ROLE`); the superadmin is only invited/replaced/promoted by the platform owner (see above) and, once assigned, can only be modified by the platform owner (409 `SUPERADMIN_PROTECTED` on any attempt to change their status or roles here, including by the superadmin themselves).

Admin-management actions — inviting, suspending/reactivating, deleting or role-assigning a `company_admin` — require `admins.invite`/`admins.manage`, held only by `tenant_superadmin`; a plain `company_admin` gets 403 `ADMIN_MANAGEMENT_FORBIDDEN` (this includes acting on *other* Company Admins, not just the superadmin — admin lifecycle is exclusively the superadmin's job now). Invite/reactivate/role-assign onto `company_admin` also enforce the tenant's `adminLimit` (409 `TENANT_ADMIN_LIMIT`). Deactivating/deleting/de-roling the tenant's last active `company_admin` is blocked (409 `TENANT_LAST_ADMIN`) only in tenants with no active superadmin yet (bootstrap fallback for tenants not yet migrated to a superadmin); once a superadmin is active, the Company Admin count may drop to zero. The "keep at least one active superadmin" side of the same invariant doesn't need its own count check: `SUPERADMIN_PROTECTED` already blocks every status/role change against a superadmin target unconditionally, and the only flows that change who the active superadmin is (`POST .../superadmin/promote`, accepting a superadmin invite) always activate the replacement before deactivating the previous one, so the active count never transiently reaches zero.

Two of the tier's tightenings land here. `status` is now refused when it falls outside `active`/`suspended`/`invited`: `normalizeUserStatus` dropped anything else to `null` and `status ? { status } : {}` then wrote nothing, so a typo returned 200 having left a suspended admin active. And `roleCodes` is checked entry by entry against the same three codes this controller has always accepted — `normalizeRoleCodes` *filtered* unrecognised entries rather than refusing them, so `["field_representative", "compny_admin"]` invited someone as a rep alone under a 200 (a whole array of typos did surface, via "at least one valid role is required", which is exactly why the mixed case slipped through). `firstName`/`lastName` are capped at 120, the same `TEXT_LIMITS.name` `normalizeNamePart` already enforced by discarding the value. `phone` deliberately carries no cap: an unchanged phone passes through unvalidated so a legacy row stays editable, and a cap here is the one thing that could refuse the admin screen's own round-trip of that stored value.

### Storage — `/storage/objects` (`storage.controller.ts`)

| Method & path                                         | Permissions                                                | Body                    | Returns                                      |
| ----------------------------------------------------- | ---------------------------------------------------------- | ----------------------- | -------------------------------------------- |
| `GET /storage/objects/:storageObjectId`               | any: `visits.read_own`, `visits.read_team`, `imports.read` | —                       | `StorageObject` metadata                     |
| `POST /storage/objects/:storageObjectId/upload-url`   | any: `visits.update_own`, `imports.upload`                 | `{ expiresInSeconds? }` | `{ url, method: "PUT", expiresAt, headers }` — re-signs the PUT (e.g. for a retry) against the object's already-registered `sizeBytes`; 400 `STORAGE_OBJECT_SIZE_UNKNOWN` for an object with none (registered before the size became mandatory) |
| `POST /storage/objects/:storageObjectId/download-url` | any: `visits.read_own`, `visits.read_team`, `imports.read` | `{ expiresInSeconds? }` | `{ url, method: "GET", expiresAt, headers }` |

Both URL-minting routes are on the [class-validator DTO track](#routes-on-the-class-validator-dto-track), through one `CreatePresignedUrlDto` — the two bodies are the same single field and always have been. What the gate buys here is the refusal of an undeclared property, not a tighter `expiresInSeconds`: that stays number-or-string (`normalizeSignedUrlTtl` `Number()`s whatever arrives, and `""`/`null` both mean "use the default"), and the 1–900 range stays with the service, whose `SIGNED_URL_TTL_INVALID` names the bounds.

Purpose-level access checks inside `StorageService` are stricter than the guard-level permission union: `import_file` needs `imports.*`, `temporary_audio`/`temporary_transcript`/`visit_attachment` need `visits.*` (+ ownership for own-scope), and `branding_logo` needs `tenant.settings.manage` to write / `tenant.settings.read` to read.

Every presigned PUT signs `Content-Length` against the object's declared `sizeBytes` (`s3-storage.client.ts`), so R2 itself refuses a body of any other length — not returned in `headers` (a browser's fetch/XHR computes it from the request body and won't let a caller override it, the same as `Host`), so the client sends nothing extra; it only has to PUT the exact bytes it declared at registration.

Writing a visit artifact requires a matching creator, not merely a non-conflicting one: an object whose `createdByUserId` is null is writable by nobody. `temporary_transcript` rows are written by the AI worker with no request context and so carry no creator, and while an absent creator counted as unowned, every transcript in the tenant was a presigned PUT any rep could ask for. The register endpoints stamp the caller on the object and mint the first URL through the same check, so nothing legitimate reaches this path without one. Reads stay deliberately wider — `visits.read_team` lets a manager reach any artifact on a visit they can see, which is how a report's problem photo renders for them.
